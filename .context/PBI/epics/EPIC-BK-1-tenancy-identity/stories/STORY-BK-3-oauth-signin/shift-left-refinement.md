## Phase 1 — Critical Analysis

### Business context

- **Primary persona affected**: Elena (Senior QA Engineer), Sara (Developer) — both need to join Bunkai using existing identity providers without creating yet another credential set.
- **Secondary personas**: Mateo (QA Lead) — workspace creation on first login feeds his team-admin workflow. Karim (AI Agent) — downstream; agents use PATs, not OAuth, but first-login workspace bootstrap affects the workspace Karim will later target.
- **Business value proposition**: Lowers the sign-up friction barrier by leveraging trusted identity providers (GitHub, Google). Removes the need for users to manage a Bunkai-specific password. First impression of the product — if this flow breaks, no other value is delivered.
- **KPI(s) influenced**: Sign-up conversion rate (activation funnel in PostHog). Time-to-first-workspace (critical onboarding KPI in `executive-summary.md §3`).
- **User journey position**: Journey 1, Step 1 — the very first action before any workspace, project, or ATC can exist. Auth is the root of the dependency cascade: `Auth → RLS → ATC create → Run execution` (master-test-plan §6).

### Technical context

- **Frontend**: `app/(auth)/login/page.tsx` — login page UI. GitHub and Google OAuth buttons currently rendered as **disabled** (`disabled`, `cursor-not-allowed`, `opacity-60`) with label "soon". This is a **CRITICAL IMPLEMENTATION GAP** for BK-3: the OAuth provider buttons have not been wired to Supabase Auth yet.
- **Backend — callback route**: `app/auth/callback/route.ts` — currently handles magic-link OTP exchange only (`exchangeCodeForSession` with `code` param). The same `/auth/callback` route is the standard Supabase Auth PKCE callback used for OAuth as well, so it will serve BK-3. However the current code comment says "Magic-link OTP exchange handler" — no OAuth-specific handling has been added.
- **Backend — middleware**: `middleware.ts` — JWT session validation via `supabase.auth.getUser()`. Protects `/projects` and `/onboarding`. `/auth` prefix is in `PUBLIC_PREFIXES`, which is correct for the callback route.
- **Backend — Supabase server client**: `lib/supabase/server.ts` — standard `@supabase/ssr` `createServerClient` with cookie read/write. Used by the callback route.
- **External services**: Supabase Auth (GitHub OAuth provider config, Google OAuth provider config). GitHub OAuth app registered in GitHub developer settings. Google OAuth credentials in Google Cloud Console. Both must be configured in the Supabase Auth dashboard with redirect URI pointing to `/auth/callback`.
- **Integration points specific to this Story**:
  - OAuth state param generated by Supabase Auth client → round-trips through provider → validated server-side in callback
  - `supabase.auth.signInWithOAuth({ provider: 'github' | 'google', options: { redirectTo: '/auth/callback' } })` — not yet called from the frontend
  - First-login workspace bootstrap (FR-001): on `exchangeCodeForSession` success, if this is the user's first verified login, a default workspace row + `workspace_members(role=owner)` must be created. This logic is **not visible in the current callback route** — it may need to be added.

### Story complexity

| Axis | Rating | Why |
|---|---|---|
| Business logic | High | State token validation, `EMAIL_EXISTS` collision, first-login workspace bootstrap, provider fallback on error |
| Integration | High | Two external OAuth providers (GitHub, Google), Supabase Auth PKCE flow, session cookie management |
| Data validation | Medium | State param integrity, email deduplication across providers, `provider` field upsert on `auth.users` |
| UI | Low | Two disabled buttons become enabled; success/failure redirects. No complex form logic. |

**Estimated test effort**: High — 3-5 QA sessions. OAuth flows require a live browser + real provider consent screens (or mock providers in Supabase local dev). State-tampering tests require URL manipulation. `EMAIL_EXISTS` scenario requires two accounts with the same email on different providers.

### Epic-level inheritance (BK-1 — Tenancy & Identity)

- **Risks restated at Story level**: Auth is the root of the dependency cascade — RLS policies depend on a valid `auth.users` row and `workspace_members` entry. If the first-login bootstrap races or fails silently, the entire permission model breaks for that user.
- **Integration points inherited**: Supabase Auth (shared with BK-2 magic-link), `workspace_members` table, `activity_log`.
- **PO/Dev answers already given at epic level**: OAuth providers (GitHub, Google) confirmed in MVP scope. Supabase Auth is the Cloud-edition auth layer (Better Auth is Phase 2 Community substitution).
- **Test strategy inherited**: Security-critical (master-test-plan §1 CRITICAL priority). State-token validation is item #1 on the pre-release checklist.

## Phase 3 — Refined Acceptance Criteria

### Original scenario: Visitor clicks "Continue with GitHub" (Happy Path)

#### Scenario 1.1: Should complete GitHub OAuth sign-up and redirect to workspace on first login (Type: Positive, Priority: Critical)
- **Given**: Visitor is on `/login`, not authenticated; GitHub OAuth app is configured in Supabase Auth with redirect URI `{BASE_URL}/auth/callback`; no `auth.users` row exists for the GitHub account email
- **When**: Visitor clicks "Continue with GitHub" → grants consent on GitHub → provider redirects to `/auth/callback?code=AUTH_CODE&state=VALID_STATE`
- **Then**:
  - UI: Browser lands on `/home` (or `/projects` — see Contradiction C1) with an authenticated session
  - API: `GET /me` returns `200` with `user_id`, `email`, `active_workspace`
  - DB (`auth.users`): one new row with `email`, `raw_app_meta_data.provider = 'github'`
  - DB (`workspace_members`): one new row with `user_id`, `role = owner`, `status = active` pointing to the new default workspace
  - DB (`activity_log`): one row for workspace creation event
  - System state: HttpOnly session cookie set in browser; `supabase.auth.getUser()` returns the user on subsequent requests

#### Scenario 1.2: Should complete Google OAuth sign-up and redirect to workspace on first login (Type: Positive, Priority: Critical)
- **Given**: Same as 1.1 but using the Google provider
- **When**: Visitor clicks "Continue with Google" → grants consent → provider redirects to `/auth/callback?code=AUTH_CODE&state=VALID_STATE`
- **Then**: Same as 1.1 with `raw_app_meta_data.provider = 'google'`

#### Scenario 1.3: Should renew session for returning OAuth user without creating a duplicate workspace (Type: Positive, Priority: High)
- **Given**: `auth.users` row already exists for the GitHub account; `workspace_members` with `role = owner` already exists; user is NOT currently authenticated
- **When**: User completes GitHub OAuth flow again
- **Then**:
  - UI: Redirect to `/home`, session active
  - DB: No new `auth.users` row; no new `workspace_members` row; no new `workspaces` row
  - System state: previous session refreshed / replaced

### AC: State token validation (Business Rule)

#### Scenario 2.1: Should reject callback with tampered state token with 403 (Type: Negative, Priority: Critical)
- **Given**: A valid OAuth flow was initiated for GitHub (Supabase Auth generated a state token)
- **When**: Browser arrives at `/auth/callback?code=VALID_CODE&state=TAMPERED_STATE` (state altered manually or via CSRF)
- **Then**:
  - API: `exchangeCodeForSession` returns an error (Supabase validates PKCE state internally)
  - UI: Redirect to `/login?error=otp_exchange_failed&reason=...`
  - DB: No `auth.users` row created; no session cookie set
  - Security: Request must NOT result in an authenticated session under any circumstances

#### Scenario 2.2: Should reject callback with missing state token (Type: Negative, Priority: Critical)
- **Given**: Direct browser navigation to `/auth/callback?code=SOME_CODE` with no `state` param
- **When**: Route handler processes the request
- **Then**:
  - API: `exchangeCodeForSession` returns error
  - UI: Redirect to `/login?error=otp_exchange_failed`
  - DB: No session created

- **When**: User attempts to sign in via Google OAuth using the same `email = "shared@example.com"` (Google account email is verified)
- **Then**:
  - UI: Redirect to `/login?error=email_exists` (exact error code TBD — NEEDS PO/DEV CONFIRMATION)
  - API: No new `auth.users` row; no new session
  - System: No automatic linking (manual linking by support in MVP)
  - Magic-link fallback CTA visible on error page

### AC: Provider error / user denies consent

#### Scenario 4.1: Should redirect to login with error when user denies GitHub OAuth consent (Type: Negative, Priority: High)
- **Given**: User is on GitHub consent screen
- **When**: User clicks "Cancel" / "Deny" → provider redirects to `/auth/callback?error=access_denied&error_description=...`
- **Then**:
  - UI: Redirect to `/login?error=otp_exchange_failed&reason=access_denied` (or equivalent)
  - Magic-link fallback CTA visible
  - DB: No session; no user row
  - **NEEDS PO/DEV CONFIRMATION**: exact error code and message for denied-consent path

#### Scenario 4.2: Should redirect to login with error when OAuth provider is unreachable (Type: Negative, Priority: High)
- **Given**: GitHub or Google OAuth service returns a network error or 5xx during code exchange
- **When**: `exchangeCodeForSession` throws an exception
- **Then**:
  - UI: Redirect to `/login?error=otp_exchange_failed&reason={encoded_message}`
  - Magic-link fallback CTA visible
  - DB: No session

## Critical Questions for PO

> These BLOCK sprint planning until answered.

1. **What is the canonical post-OAuth-login redirect destination: `/home` or `/projects`?**
   - **Context**: Story workflow says "Redirect to `/home`" but current callback code defaults to `/projects` (Contradiction C1). Both cannot be correct.
   - **Impact if unanswered**: Success-path test will fail on the wrong URL; the redirect target must be locked before Dev implements the callback.
   - **Suggested answer**: Define `/home` as the canonical post-login landing page and update the callback route default AND add a `/home` route to the app.

2. **What is the exact error code and user-facing message for the `EMAIL_EXISTS` scenario?**
   - **Context**: Business rule says "rejected with `EMAIL_EXISTS`" but does not specify: (a) which URL the user lands on, (b) what message they see, (c) whether the rejection happens at Supabase Auth level or app level.
   - **Impact if unanswered**: Cannot write the negative test for provider collision. Risk of information disclosure (message revealing that an account exists).
   - **Suggested answer**: Redirect to `/login?error=email_exists` with a message "An account with this email already exists — sign in with your original provider or contact support to link accounts."

3. **Should invited users be exempt from the default workspace bootstrap on first OAuth login?**
   - **Context**: Story says "if first verified login, default workspace created" — but an invited user already belongs to a workspace. Creating a second personal workspace wastes data and confuses the user (Edge E8).
   - **Impact if unanswered**: Invited users end up with two workspaces; the active workspace selection at login is undefined.
   - **Suggested answer**: If an active `workspace_invites` row exists for the user's email at the time of first login, skip the personal workspace bootstrap and instead accept the invite.

## Technical Questions for Dev

> These do not block PO but block implementation.

1. **Does Supabase Auth's PKCE state validation cover all attack vectors (state missing, state replayed, state tampered)?** — Confirm whether `exchangeCodeForSession` covers all three cases internally or if the callback route needs to add its own validation layer. Testing cannot be scoped until this is confirmed.

2. **What is the correct handling for an unverified OAuth provider email?** — Is Supabase Auth configured to block unverified emails by default, or does Bunkai need to add a check in the callback after token exchange? If the email is unverified, what is the error path?

3. **Is the `safeNext` check in `app/auth/callback/route.ts` sufficient to prevent all open-redirect variants?** — Current check: `next.startsWith('/') && !next.startsWith('//')`. This blocks `//evil.com` but not `%2F%2Fevil.com` (URL-encoded) or other bypass patterns. Should use a URL parser to extract just the pathname instead of string matching.

4. **How does the first-login workspace bootstrap interact with the `workspace_invites` flow in BK-1?** — Is there a shared service function, or will BK-3 implement its own bootstrap separate from the invite-acceptance flow?

5. **Will the OAuth buttons in `login/page.tsx` be enabled as part of this ticket, or is there a separate UI-unlock ticket?** — The buttons are currently hardcoded as `disabled`. This must be part of BK-3's implementation scope.
