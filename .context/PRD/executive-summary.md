## 1. Problem Statement

### The Challenge

Test Management Systems on the market today (Xray, Zephyr Scale, TestRail, qTest) are, in the target team's own framing, "document vaults with execution glued on top": each test case is a monolithic blob of free-form steps stored in a folder, with no structural enforcement. Steps are duplicated across dozens of tests, traceability between User Story, Acceptance Criterion, Test, Run, and Bug is "a free-text field if you remember to fill it," and reports show "80% passing" without telling anybody what those 80% actually validate.

Source: `upex-bunkai-tms/.context/PRD/executive-summary.md:12-19` (quoted verbatim in `bunkai-qa-engineering/.context/business/business-model.md:12-14`).

This is not just stated intent — it is corroborated by the shipped data model. `business-data-map.md:60` confirms the rule this problem statement motivates is a real, enforced constraint: **every ATC must be anchored to a User Story AND at least one Acceptance Criterion**, validated inside SECURITY DEFINER RPCs (`bunkai_create_atc`/`bunkai_update_atc`) before any write commits. The traceability-chain report (`GET /api/v1/projects/{id}/traceability`) is a direct, working answer to "nobody can answer 'what does this story cover?' with certainty."

### Current Alternatives

## 2. Solution Overview

### Product Vision (one sentence)

Bunkai is a Test Management System that makes traceability a database-enforced invariant (User Story → Acceptance Criterion → ATC → Test → Run → Bug), not an optional free-text field, so a QA Lead can prove test coverage instead of asserting it.

### Core Capabilities

| # | Feature | Problem Addressed | Evidence (route or component) |
|---|---|---|---|
| 1 | ATC authoring with mandatory US/AC anchoring | Free-floating, undocumented test cases; the industry's core traceability gap | `POST /api/v1/atcs` → `bunkai_create_atc` RPC; `components/atcs/NewAtcEditor.tsx` |
| 2 | Test chains with reuse ("one-edit-many-tests") | Duplicated step text across dozens of tests, drift when one changes | `POST /api/v1/tests`, `test_steps` table; edit response returns `affected_test_count` |
| 3 | Manual Run execution (per-step Pass/Fail/Blocked, evidence) | "80% passing" reports with no record of what was actually exercised | `POST /api/v1/runs`, `.../steps/{id}/mark`, `.../finish`; `components/runs/RunnerView.tsx` |
| 4 | Native defect management anchored to Module + ATC + Run | Bugs delegated to a separate tracker with no structural link back to the failing step | `POST /api/v1/bugs`; DB trigger `bugs_check_consistency` |
| 5 | Traceability Chain Report (US → ATC → Test → Run → Bug in one read) | No single view answering "is this story covered, and did the covering tests pass?" | `GET /api/v1/projects/{id}/traceability`; `components/traceability/TraceabilityChainView.tsx` |

Source for all five: `bunkai-qa-engineering/.context/business/business-feature-map.md` (Domains: ATC Library, Tests, Manual Execution, Defects, Traceability).

**Not in the top 5 (still shipped, see feature-map for the full 55-feature catalog)**: Workspace/Project/Module hierarchy management, Personal Access Token (PAT) issuance for agentic/CI callers, Notifications, Milestones, Home/Coverage/Activity dashboards, Jira story import.

### Key Differentiators

- **"One-edit-many-tests" propagation** — editing a reusable ATC updates every Test that chains it; the edit API response returns `affected_test_count` as a concrete, verifiable mechanism, not marketing copy. Source: `business-model.md:31`; `business-api-map.md` Journey 4.
- **Structural (DB-enforced) traceability**, not a documentation convention — an ATC literally cannot be created without an anchoring User Story + Acceptance Criterion (`atcs.user_story_id NOT NULL`, FK RESTRICT, RPC pre-check). Source: `domain-glossary.md` BR-01.
- **API-first for AI/agent operators** — Bearer PAT auth with scoped capabilities (`atc:read`, `atc:write`, `run:execute`, `workspace:admin`), idempotency keys on Run start, and a single unified `withApiHandler()` gateway with a consistent error envelope. This is a first-class design goal (see Persona "Karim" in `user-personas.md` below), not incidental API hygiene. Source: `business-api-map.md` §2, §4.

## 5. Product Scope

### What's Included (current capabilities)

- Full auth surface: magic-link, password + mandatory OTP sign-up, OAuth (Google/GitHub), headless PAT auto-mint.
- Workspace/Project/Module hierarchy (multi-tenant, tree-structured modules, depth ≤ 6).
- ATC authoring (REST, unified browser+machine path) with mandatory US/AC anchoring.
- Test chain assembly, reorder, tagging (`smoke`/`sanity`/`regression` reserved suite tags).
- Manual Run execution end-to-end: start (idempotent) → per-step mark → abort/finish → history/reporting.
- Native Bug tracking anchored to Module + ATC + Run, forward-only status lifecycle, assignment.
- Traceability Chain Report with filters and a client-side HTML export.
- Realtime Notifications (bell + toast), Milestones, Home/Coverage/Activity dashboards.
- Jira story import (one-directional, async).

Source: `business-feature-map.md` (55 features, 48 Stable).

### What's Not Included (known limitations)

- **Self-hosted "Bunkai Community" distribution** — central to the stated business model but confirmed absent in code (no object-storage SDK, no alternate DB adapter). Source: `business-model.md` Discovery Gaps.
- **Billing/subscription enforcement** — `workspaces.plan` field exists and is CHECK-constrained but zero billing logic gates on it.
- **Agentic and automated (CI/CD) execution modes** — only Manual execution is shipped; the "three unified execution modes" value prop is partially shipped only.
- **Email delivery** for workspace invites — `RESEND_API_KEY` unused by app code; invite links are returned in the API response body only, shared out-of-band.
- **Error tracking / observability** (Sentry, PostHog) — described in architecture docs, not implemented.
- **Feature-flag system** — `feature_flags` table exists but is queried zero times anywhere in the codebase; fully dead.

## 7. QA Relevance

### Critical Testing Areas

- **ATC anchoring invariant (BR-01)** — the product's single highest-value regression check; every release should include a negative test attempting to create an ATC without a US/AC.
- **Manual Run execution lifecycle** — start (idempotency-key required) → mark → abort (DB-enforced reason) → finish (auto-skip pending steps) is the newest, most structurally load-bearing domain (shipped since June).
- **Bug consistency trigger** — `bugs_check_consistency` must reject a crafted cross-run/cross-project payload at the DB layer, not just app validation.
- **Traceability non-disclosure** — cross-workspace story access must always 404, never 403 (anti-enumeration design).

### Risk Areas

- PAT issuance (FEAT-005) and Workspace switching (FEAT-009) both carry recently-patched security bugs (BK-134/135, BK-316) — regression-test the fixed behavior on every release, not just once.
- No CI/CD pipeline in the target repo — release confidence depends entirely on this companion QA-engineering repo's suites running manually against `staging` before a ticket is marked `Tested`. See `CLAUDE.md` §"Project Assessment (Phase 1)".
