## 1. Performance

### NFR-PERF-001: Home Coverage Rollup Caching

| Aspect | Value |
|---|---|
| **Target** | Not stated as an SLA — the mechanism exists to avoid a *repeated* full per-project sweep, not to hit a latency number |
| **Implementation** | In-process `Map<string, {expiresAt, value}>` TTL memo, `HOME_COVERAGE_CACHE_TTL_MS = 60_000` (60s). Deliberately NOT Next's `unstable_cache` (the request-scoped Supabase client's session refresh reaches for cookies — a dynamic API incompatible with a cache scope). Only a **complete** rollup is ever cached — a transient RPC error is never pinned into the cache. |
| **Evidence** | `lib/home/coverage.ts:313-359`, `lib/home/constants.ts:118` |

**Stated limitation (self-documented in code, not inferred)**: the cache is per-serverless-instance, not shared — "a cold serverless instance always pays full price, and N instances mean up to N sweeps per TTL instead of one." Named upgrade path (Redis / Next Data Cache) is not built.

### NFR-PERF-002: Database Query Optimization (Indexes)

| Aspect | Value |
|---|---|
| **Target** | Not stated — no query-latency benchmark found |
| **Implementation** | 60+ non-PK indexes across `public` schema (live count), several **partial** (predicate-filtered) and tuned to specific hot list views: `bugs_workspace_id_severity_unresolved_idx` (`WHERE status IN ('open','in_progress')`), `runs_workspace_id_started_at_running_idx` (`WHERE status='running'`), `notifications_recipient_workspace_unread_idx` (`WHERE read_at IS NULL`). Several composites are shaped for keyset pagination (`created_at DESC, id DESC`). Full-text search backed by a GIN index on `atcs.tsv`, maintained by the `atcs_refresh_tsv` trigger. |
| **Evidence** | Live `pg_indexes` query against `staging`, `public` schema |

## 2. Security

### NFR-SEC-001: Authentication Model

| Aspect | Value |
|---|---|
| **Target** | Every `/api/v1/**` route authenticated unless explicitly opted into `auth: 'public'` (secure-by-default) |
| **Implementation** | Dual scheme collapsed into one `Principal` type — Supabase session cookie (browser) OR Bearer PAT `bk_pat_<prefix>.<secret>` (machine). Bearer is checked first so an explicit PAT is never shadowed by a stale cookie. PAT secret is SHA-256-hashed and stored in a **sibling table** (`access_token_secrets`, not on `access_tokens` itself) specifically so read-access-only roles cannot recover it. |
| **Evidence** | `lib/api/principal.ts`, `lib/api/middleware/bearer.ts`, `lib/api/handler.ts` |

### NFR-SEC-002: Authorization Model (RLS-First)

| Aspect | Value |
|---|---|
| **Target** | Every table's row-level access decided by Postgres, not re-implemented in TypeScript |
| **Implementation** | 85 RLS policies across all 28 `public` tables (live count), gated through 2 shared predicate functions confirmed live: `bunkai_is_workspace_member()` (read) and `bunkai_can_write_workspace()` (write, role ≥ `member`). A PAT's data access runs through an anon client carrying a short-lived per-user JWT (never the service-role key) so `auth.uid()` resolves identically for both auth schemes. |
| **Evidence** | live `pg_policies` query; `lib/api/principal.ts:106-123` (`impersonatingClient`) |

### NFR-SEC-003: Capability / Scope Enforcement (PAT)

| Aspect | Value |
|---|---|
| **Target** | A Bearer PAT can only perform actions within its minted scopes; an admin-scoped PAT can only act on its bound workspace |
| **Implementation** | 4 scopes (`atc:read`, `atc:write`, `run:execute`, `workspace:admin`); cookie sessions implicitly hold all 4. `assertWorkspaceContext()` re-checks the workspace binding on **every** call, not just at mint time. Issuance itself is role-gated (`assertTokenIssuanceAuthorized` — BK-134/135 fix): `workspace:admin` requires active membership + `admin`/`owner` role in the SPECIFIC target workspace. |
| **Evidence** | `lib/api/pat.ts:53-89`, `lib/api/principal.ts:91-104` |
| **Residual risk (not this pass's fix)** | `business-api-map.md` GAP-14: ~136 pre-fix `workspace:admin` PATs minted on `staging` before BK-134/135 landed were not confirmed revoked. |

### NFR-SEC-004: Input Sanitization — Markdown

| Aspect | Value |
|---|---|
| **Target** | User-authored Markdown (ATC/Story/AC bodies) renders safely, no script injection |
| **Implementation** | `react-markdown` + `remark-gfm` + `rehype-sanitize` pipeline. Content-length budget enforced at filing time (`MAX_ATC_CONTENT_BYTES = 2048`, UTF-8-byte-measured via a custom `byteLength()`, not Zod `.max()` which counts UTF-16 units — deliberate, to measure multibyte input the same way for every writer). |
| **Evidence** | `package.json` (`rehype-sanitize` dependency); `lib/atcs/validation.ts:14,19` |

### NFR-SEC-005: Input Sanitization — URL Scheme Allowlist (BK-337 fix)

| Aspect | Value |
|---|---|
| **Target** | Evidence URLs (Bug filing, Run-step marking) can never carry a `javascript:`/`data:`/other dangerous scheme |
| **Implementation** | Zod 4.4.3's `z.url({ protocol: z.regexes.httpProtocol })` (`/^https?$/`) replaces a prior bare `z.string().url()` that accepted ANY parseable scheme. Filing-time control; a companion render-time allowlist (`isHttpUrl`, `lib/utils/url.ts`) is the load-bearing control for rows stored **before** this fix. |
| **Evidence** | `lib/bugs/validation.ts:34-42` (code comment names the CVE-class explicitly: "BK-337 (TQ5)... tightened... javascript:/data: payloads") |

> **Flag for prominent QA attention**: this is a confirmed, fixed XSS-class vulnerability with a documented before/after — a strong candidate for a dedicated regression test (submit `javascript:alert(1)` as an evidence URL, assert 422, then separately verify a row written before the fix still renders safely via the client-side allowlist).

### NFR-SEC-006: Non-Disclosure / Anti-Enumeration Pattern

| Aspect | Value |
|---|---|
| **Target** | Cross-workspace/foreign/missing-entity lookups never leak WHICH case occurred |
| **Implementation** | Repeated pattern across ≥4 independent code paths: Bearer-token verification (missing/malformed/unknown/expired/revoked all → uniform 401), Bug assign/status-transition (missing bug vs. bug in an unreachable workspace → same `not_found`), Traceability query (missing/foreign/wrong-project Story → always 404, never 403), OTP confirm (wrong code vs. no pending signup → uniform 401). |
| **Evidence** | `lib/api/middleware/bearer.ts` header comment; `lib/bugs/errors.ts` comment; `business-feature-map.md` FEAT-050; `app/api/v1/auth/confirm/route.ts` |

## 3. Reliability

### NFR-REL-001: Unified Error Envelope

| Aspect | Value |
|---|---|
| **Target** | Every `/api/v1/**` error response follows one shape, always |
| **Implementation** | `{ error: { code, message, details?, request_id? } }` via `withApiHandler`'s centralized `toApiError()` — `ApiError` instances pass through, `ZodError` maps to `validation_failed` (422), anything else maps to `internal_error` (500) with the request-id attached so a user can quote it in a bug report. |
| **Evidence** | `lib/api/handler.ts:94-125`, `lib/api/error-envelope.ts` |

### NFR-REL-002: Request-ID Propagation

| Aspect | Value |
|---|---|
| **Target** | Every response, success or failure, carries `x-request-id` |
| **Implementation** | Inbound header honored if present, otherwise a fresh UUID minted; set on the response headers unconditionally in `withApiHandler`. |
| **Evidence** | `lib/api/handler.ts:66,84,97`, `lib/api/request-id.ts` |

### NFR-REL-003: Structured Access Logging

| Aspect | Value |
|---|---|
| **Target** | Every request logged with enough shape to correlate with a user report |
| **Implementation** | `logRequest()` emits structured JSON to stdout (Vercel-indexable) on both success and failure paths — `{ request_id, method, path, status, duration_ms, error_code?, message? }`. Severity: `info` for 2xx/3xx, `warn` for 4xx, `error` for 5xx. |
| **Evidence** | `lib/api/handler.ts:85-91,98-106`, `lib/api/logging.ts` |

### NFR-REL-004: External-Call Resilience (Jira Import)

| Aspect | Value |
|---|---|
| **Target** | Jira 429s do not fail the import outright |
| **Implementation** | Exponential backoff schedule for 429s, length caps the retry count; honors a numeric `Retry-After` header when present, falls back otherwise. Per-issue errors are surfaced individually, not job-level — one bad Story does not fail the whole import batch. |
| **Evidence** | `lib/jira/client.ts:78-151` |
| **Scope note** | This is the ONLY outbound integration with retry logic. **No equivalent resilience found for Supabase calls** — a transient Postgres/PostgREST error is not retried anywhere in the reviewed code paths. |

### NFR-REL-005: Idempotency / Replay Safety

| Aspect | Value |
|---|---|
| **Target** | A network-retried `POST /runs` never creates a duplicate Run |
| **Implementation** | Two independent layers: HTTP-level `Idempotency-Key` header (`lib/api/idempotency.ts`, unique on `(user_id, endpoint, key)`, pattern `^[\w-]{8,128}$`) and a domain-level `start_token` 24h dedup window inside `bunkai_create_run`. A throw before the RPC commits discards the pending key so it does not strand; a snapshot-store failure after a successful RPC does not fail the request. |
| **Evidence** | `lib/api/idempotency.ts`; `app/api/v1/runs/route.ts` |

### NFR-REL-006: Health Check Endpoint

| Aspect | Value |
|---|---|
| **Target** | Unknown |
| **Implementation** | `app/api/v1/health` directory exists (confirmed in the route listing) but its handler body was not read this pass — presence confirmed, behavior (what it actually checks — DB connectivity? just liveness?) not verified. |
| **Evidence** | `find app/api/v1 -maxdepth 1 -type d` output includes `health` |

### NFR-REL-007: DB-Layer Backstops Independent of App Validation

| Aspect | Value |
|---|---|
| **Target** | A crafted request bypassing app-layer validation is still rejected where a DB-layer guard exists |
| **Implementation** | Confirmed for 2 invariants: `runs_abort_reason_chk` CHECK constraint (BR-02) and `bugs_check_consistency` BEFORE INSERT/UPDATE trigger (BR-03). **Confirmed absent** for `bugs.status` transition ordering (BR-04 — app-enforced only) and **not verified either way** for Bug-filing's "step must be failed" rule (BR-New-2 in functional-specs.md). |
| **Evidence** | `domain-glossary.md` BR-02/BR-03/BR-04; `functional-specs.md` FR-004 Discovery Gaps |

## QA Relevance

### Testable NFRs and suggested tooling

| NFR | Testable? | Suggested Tool |
|---|---|---|
| NFR-PERF-001 (coverage cache) | Yes — assert a second Home load within 60s returns from cache (e.g. via response-time delta or a deliberately-changed-then-still-stale read) | Playwright + manual timing, or a direct API timing harness |

| NFR-SEC-006 (non-disclosure) | Yes — compare the exact response body/status for "wrong OTP" vs. "no such signup," and for "missing bug" vs. "bug in an unreachable workspace" — assert byte-identical shape | API test suite |

| NFR-REL-005 (idempotency) | Yes — fire two concurrent `POST /runs` with the identical `Idempotency-Key`, assert exactly one Run row created | API test suite, possibly with an artificial race via parallel requests |
| NFR-OBS-001/002/003/004/005 (observability absence) | Testable as an ABSENCE assertion only — e.g. confirm no Sentry/PostHog script tag loads in the browser, no `@sentry` init call fires | Playwright network-request inspection |
