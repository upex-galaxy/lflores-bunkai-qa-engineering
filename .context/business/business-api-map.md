# Business API Map: Bunkai TMS

---

## 1. Executive Summary

Bunkai's API has two kinds of callers: human users navigating the browser app, and machine callers (CLI tools, AI agents, CI pipelines) consuming the REST layer directly. Both reach the same 21 endpoints under `/api/v1/`, but through different auth schemes — browser users carry a Supabase session cookie while machine callers present a short-lived Bearer PAT (`bk_pat_*`). Every endpoint that touches workspace data is further bounded by Supabase Row Level Security, so a valid token only ever sees the workspaces it belongs to.

The product's core value is concentrated in two flows: establishing a workspace (onboarding + invite) and authoring ATCs (Atomic Test Components anchored to User Stories and Acceptance Criteria). Everything else in the API — profile introspection, token management, workspace switching — exists to support these two journeys. The ATC authoring flow bypasses the REST API entirely: the browser calls a Supabase SECURITY DEFINER RPC (`bunkai_save_atc`) directly as a Server Action, not via `/api/v1/`.

The API is served as Next.js 15 Route Handlers running in Node.js. There is no separate API gateway. Multi-tenancy is enforced at the database layer (Supabase RLS) rather than at the handler layer, which means a handler can trust that any Supabase client query is already scoped to the caller's accessible workspaces.

## 2. Permission & Auth Model

### Tier taxonomy

| Tier | Who it applies to | How to acquire | Where enforced (code path) |
|---|---|---|---|
| **Public** | Unauthenticated callers, bots, docs consumers | No token needed | `withApiHandler` wrapper — no auth check |
| **Cookie (Supabase Session)** | Browser users | OTP exchange at `GET /auth/callback` OR password sign-in via `POST /api/v1/auth/signin` | `requireAuth()` in `lib/api/auth.ts` → `createClient().auth.getUser()` |
| **Bearer PAT** | CLI, AI agents, CI pipelines | `POST /api/v1/tokens` (session required) OR auto-minted by `POST /api/v1/auth/signin` / `POST /api/v1/auth/signup` | `requireBearerToken()` in `lib/api/middleware/bearer.ts` → prefix lookup + SHA-256 hash compare in DB |
| **RLS (DB-layer)** | Every DB query regardless of auth scheme | Implicit — Supabase applies it on every query | Supabase Postgres policies on all tables |

> **Priority rule**: `requireAuth()` checks Bearer first. A request that sends both `Authorization: Bearer` and a session cookie uses Bearer. A stale cookie never shadows an explicit PAT.

> **Scope model**: Cookie sessions have `scopes: []` — the browser user's permission is governed by RLS only. Bearer PATs carry explicit scopes (`atc:read`, `atc:write`, `run:execute`, `workspace:admin`). Endpoints that gate writes for machine callers use `requireScopeOrCookie(ctx, scope)` — this lets browser users through unconditionally while checking the scope for Bearer callers.

## 3. Critical Business Journeys

### Journey 1 — New user onboarding (browser)

**Business purpose**: A brand-new user authenticates via magic link and creates their first workspace so they can start a project.

```
Browser            /api/v1                Supabase Auth       DB (RLS)
  |                   |                       |                  |
  |--POST /auth/magic-link {email} --------> OTP enqueue        |
  |<-- 200 ok --------|                       |                  |
  |  [clicks email]   |                       |                  |
  |--GET /auth/callback?code ---------------  exchangeCodeForSession
  |<-- 302 /onboarding (no workspace yet) ---|                  |
  |                   |                       |                  |
  |  [fills slug+name in OnboardingForm]      |                  |
  |-- RPC bunkai_bootstrap_workspace() ----------------------------> (SECURITY DEFINER)
  |                   |                       |          insert workspaces + workspace_members (owner)
  |<-- redirect /projects ------------------------------------- |
```

**Numbered narrative:**
1. `POST /api/v1/auth/magic-link` — no auth required; Supabase enqueues OTP email.
2. `GET /auth/callback` — exchanges OTP code for Supabase session cookies; open-redirect guard on `next` param.
3. `/projects` server component checks `workspace_members` — finds 0 rows → redirects to `/onboarding`.
4. `bunkai_bootstrap_workspace` RPC — SECURITY DEFINER; atomically inserts `workspaces` row + `workspace_members` row with `role=owner`, `status=active`. Not an API route — called as Next.js Server Action directly.
5. Redirect to `/projects` — now has a workspace, project list renders (or empty state).

**Endpoints involved**: `POST /api/v1/auth/magic-link`, `GET /auth/callback`
**Entities touched**: `magic_link_tokens`, `magic_link_token_secrets`, `workspaces`, `workspace_members`
**Feature IDs**: FEAT-001, FEAT-007

### Journey 2 — Machine / CI sign-in + PAT acquisition

**Business purpose**: A CLI tool or AI agent authenticates headlessly and gets a long-lived token to drive subsequent API calls without a browser.

```
CLI / Agent        /api/v1/auth/signin          DB
  |                       |                      |
  |-- POST {email, password, pat_scopes} ------> |
  |                       |-- signInWithPassword()-> Supabase Auth
  |                       |<-- { user, session } |
  |                       |-- mintPat() -------> insert access_tokens
  |                       |                      insert access_token_secrets (hash only)
  |<-- 200 { session, pat: { token:"bk_pat_...", scopes, expires_at } }
  |                       |                      |
  |-- [all subsequent calls] Authorization: Bearer bk_pat_...
```

**Numbered narrative:**
1. `POST /api/v1/auth/signin` — public endpoint; validates email+password against Supabase Auth.
2. `mintPat()` — generates 32-byte random secret; stores SHA-256 hash in `access_token_secrets` (sibling table — QA/analytics roles cannot read it). Raw token returned exactly once.
3. The PAT format is `bk_pat_<12-char prefix>.<remainder>`. The prefix enables O(1) DB lookup before the hash comparison, avoiding a full-table scan.
4. All subsequent Bearer calls: `requireBearerToken()` looks up by prefix, fetches hash from sibling table, compares SHA-256(prefix+remainder) in JS (constant-time). Also checks `revoked_at IS NULL` and expiry.

**Alternative start**: `POST /api/v1/auth/signup` — identical flow but creates user first via Supabase Admin API with `email_confirm: true` (no email confirmation needed for QA accounts). Returns 409 if email exists.

**Endpoints involved**: `POST /api/v1/auth/signin`, `POST /api/v1/auth/signup`, `POST /api/v1/tokens` (for extra PATs after initial sign-in)
**Entities touched**: `access_tokens`, `access_token_secrets`
**Feature IDs**: FEAT-002, FEAT-003, FEAT-005

### Journey 3 — Workspace invite + acceptance

**Business purpose**: A workspace Admin invites a teammate by email, the teammate receives the link, signs in, and joins the workspace with the assigned role.

```
Admin (browser)    /api/v1                          DB               Invitee (browser)
  |                   |                              |                     |
  |--POST /workspaces/{id}/invites {email, role} -> |                     |
  |                   |-- RLS check (admin/owner) -> workspace_invites    |
  |                   |-- insert invite row -------> |                     |
  |                   |-- insert token hash -------> workspace_invite_secrets
  |<-- 201 { invite, token, accept_url } ---------- |                     |
  |  [admin copies accept_url, sends manually]       |                     |
  |                   |                              |  [invitee opens URL]|
  |                   |                              |  GET /invites/accept?token=...
  |                   |                              |                     |
  |                   |                              |  [invitee signs in first]
  |                   |                              |  (Journey 1)        |
  |                   |                              |                     |
  |                   |<--POST /api/v1/invites/accept {token} ------------|
  |                   |-- hash lookup (invite_secrets) --> workspace_invites
  |                   |-- validate: not revoked, not expired, email match  |
  |                   |-- upsert workspace_members (role from invite) ---> |
  |                   |-- stamp accepted_at ----------------------------- |
  |                   |<-- 200 { ok, workspace_id, role } --------------- |
  |                   |                              |  redirect /projects |
```

**Numbered narrative:**
1. `POST /api/v1/workspaces/{id}/invites` — RLS gates this to admin/owner. Generates raw token, stores only SHA-256 hash in sibling table (`workspace_invite_secrets`). Returns raw token + accept URL in response exactly once. **No email sent** — admin must forward the URL manually (MVP).
2. Invitee must be authenticated (signed in) before accepting. They go through Journey 1 first if new.
3. `POST /api/v1/invites/accept` — resolves token hash → invite ID → invite metadata. Validates: not revoked, not expired (7-day TTL), caller email matches invite email. Upserts `workspace_members` row.
4. Invite status is derived (not stored): `pending` / `accepted` / `revoked` / `expired` — computed from `accepted_at`, `revoked_at`, `expires_at` at read time.

**Resend flow**: `POST /api/v1/workspaces/{id}/invites/{inviteId}` — rotates the token secret and extends expiry 7 more days. Previous accept link becomes invalid.
**Revoke flow**: `DELETE /api/v1/workspaces/{id}/invites/{inviteId}` — sets `revoked_at`. Token immediately invalid.

**Endpoints involved**: `POST /api/v1/workspaces/{id}/invites`, `GET /api/v1/workspaces/{id}/invites`, `POST /api/v1/workspaces/{id}/invites/{inviteId}`, `DELETE /api/v1/workspaces/{id}/invites/{inviteId}`, `POST /api/v1/invites/accept`
**Entities touched**: `workspace_invites`, `workspace_invite_secrets`, `workspace_members`
**Feature IDs**: FEAT-010, FEAT-011

### Journey 4 — ATC authoring (core product value)

**Business purpose**: A QA engineer creates or updates an Atomic Test Component (ATC) with steps, assertions, and links it to a User Story + Acceptance Criterion — the minimum valid test artifact in Bunkai.

```
Browser (AtcEditor)      Next.js Server            Supabase DB
  |                          |                          |
  |-- [loads /projects/{slug}/atcs/{id}]                |
  |                          |-- select project, module, atc, stories, ACs, steps, assertions
  |<-- hydrated AtcEditor -- |                          |
  |                          |                          |
  |  [user edits title, layer, tags]                    |
  |  [edits steps in Monaco markdown editor]            |
  |  [edits assertions in Monaco YAML editor]           |
  |  [selects User Story + ACs in AnchoringPanel]       |
  |                          |                          |
  |-- [click Save → Server Action saveAtcAction()]      |
  |                          |                          |
  |                          |-- RPC bunkai_save_atc(   |
  |                          |    p_atc_id, p_title,    |
  |                          |    p_layer, p_tags,      |
  |                          |    p_user_story_id,      |
  |                          |    p_steps (JSON),       |
  |                          |    p_assertions (JSON),  |
  |                          |    p_ac_ids (UUID[])     |
  |                          |  ) ----------------------> (SECURITY DEFINER)
  |                          |                          |-- upsert atcs
  |                          |                          |-- replace atc_steps
  |                          |                          |-- replace atc_assertions
  |                          |                          |-- replace atc_acceptance_criteria
  |                          |<-- { ok } -------------- |
  |<-- toast "Saved" ------- |                          |
```

**Numbered narrative:**
1. Page loads all data via Supabase client (RLS-scoped) in a Next.js Server Component — no REST call.
2. Monaco editors (`StepEditor` for markdown steps, inline YAML for assertions) are lazy-loaded client components.
3. `AnchoringPanel` requires the user to select a User Story AND at least one AC — the invariant "every ATC must be anchored" is enforced at save time.
4. Save triggers `saveAtcAction` (Next.js Server Action) which calls `bunkai_save_atc` RPC. This is **not** a REST endpoint — it bypasses `/api/v1/` entirely. The RPC is SECURITY DEFINER and performs all four table writes in a single transaction (no partial saves).
5. Steps are stored as structured rows (`atc_steps`) but edited as markdown — `stepsToMarkdown` / `stepsFromMarkdown` in `lib/atc-parse.ts` handle the round-trip. Assertions similarly use YAML.

**Endpoints involved**: None (REST API) — this journey uses Next.js Server Actions + Supabase RPC directly.
**Entities touched**: `atcs`, `atc_steps`, `atc_assertions`, `atc_acceptance_criteria`, `user_stories`, `acceptance_criteria`
**Feature IDs**: FEAT-016, FEAT-017

> **QA Implication**: ATC save cannot be tested via `/api/v1/` — tests must either use the Supabase client directly or drive the browser UI. There is no `POST /api/v1/atcs` endpoint.

### Journey 5 — PAT lifecycle (machine caller self-management)

**Business purpose**: A machine caller lists, issues, and revokes its own Personal Access Tokens — routine credential hygiene for CI/CD pipelines.

```
CLI                /api/v1                          DB
  |                   |                              |
  |-- GET /tokens (Cookie auth) -----------------> access_tokens (RLS: auth.uid() = user_id)
  |<-- { tokens: [{ id, name, scopes, token_prefix, expires_at, revoked_at }] }
  |                   |                              |
  |-- POST /tokens {scopes, name, expires_in_days} (Cookie auth)
  |                   |-- mintPat() ------> access_tokens + access_token_secrets
  |<-- 201 { token: "bk_pat_...", id, scopes, expires_at }  (token shown ONCE)
  |                   |                              |
  |  [rotate: revoke old, mint new]                  |
  |-- DELETE /tokens/{id} (Cookie auth) -----------> access_tokens.revoked_at = now()
  |<-- 204 No Content |                              |
```

**Numbered narrative:**
1. `GET /api/v1/tokens` — requires cookie session (RLS scopes by `auth.uid()`). Returns token metadata without the secret. `token_prefix` is visible for identification; the hash is in the sibling table and never returned.
2. `POST /api/v1/tokens` — requires cookie session only (PATs cannot mint PATs — intentional chicken-and-egg prevention). Mint uses `lib/api/pat.ts::mintPat()` shared with signin/signup flows.
3. `DELETE /api/v1/tokens/{id}` — soft-revoke only. Row stays in `access_tokens` as audit trail. Bearer middleware rejects rows with `revoked_at IS NOT NULL`.
4. `last_used_at` is fire-and-forget updated on every successful Bearer auth — visible in the token list for audit.

**Endpoints involved**: `GET /api/v1/tokens`, `POST /api/v1/tokens`, `DELETE /api/v1/tokens/{id}`
**Entities touched**: `access_tokens`, `access_token_secrets`
**Feature IDs**: FEAT-005

### Journey 6 — Workspace switching (multi-workspace context)

**Business purpose**: A member of multiple workspaces switches their active workspace context — subsequent DB queries and UI renders target the new workspace.

```
Browser (WorkspaceSwitcher)   /api/v1                   DB / Cookie
  |                               |                          |
  |  [user opens workspace picker, selects WS B]             |
  |-- POST /api/v1/me/active-workspace {workspace_id} -----> |
  |                               |-- supabase.from('workspaces').select().eq('id', ws_id)
  |                               |   (RLS: returns row only if caller is member)
  |                               |-- 403 if not member ---- |
  |                               |-- set bk_active_ws httpOnly cookie
  |<-- 200 { ok, active_workspace_id } ------------------- |
  |                               |                          |
  |-- [page refresh / navigation to /projects]              |
  |   Server components read bk_active_ws cookie            |
  |   All Supabase queries now return data for WS B         |
```

**Numbered narrative:**
1. `POST /api/v1/me/active-workspace` — requires Cookie auth. RLS enforces membership; a non-member gets 403 (the select returns no rows, handler maps to 403).
2. Response sets `bk_active_ws` httpOnly cookie. Does NOT touch the Supabase JWT.
3. All subsequent Server Component renders pick up the cookie and scope queries accordingly.

**Endpoints involved**: `POST /api/v1/me/active-workspace`, `GET /api/v1/me`
**Entities touched**: `workspaces`, `workspace_members`
**Feature IDs**: FEAT-009, FEAT-006

## 4. Architecture Behind the API

```
                    ┌──────────────────────────────────────────────┐
                    │               CLIENT LAYER                   │
                    │  Browser (React/Next.js) · CLI · AI Agent    │
                    └────────────────────┬─────────────────────────┘
                                         │ HTTP / Cookie / Bearer
                    ┌────────────────────▼─────────────────────────┐
                    │          NEXT.JS 15 APP ROUTER               │
                    │  Route Handlers (/api/v1/**/route.ts)        │
                    │  Server Components (read-only DB queries)    │
                    │  Server Actions (ATC save, workspace create) │
                    │                                              │
                    │  withApiHandler() — global error envelope,   │
                    │  request-id, structured logging              │
                    │                                              │
                    │  requireAuth() ──── Bearer first, cookie     │
                    │                     second; check both       │
                    └────────────────────┬─────────────────────────┘
                                         │ Supabase JS client
                    ┌────────────────────▼─────────────────────────┐
                    │              SUPABASE LAYER                  │
                    │                                              │
                    │  Auth (Supabase GoTrue) — OTP, OAuth, Pwd   │
                    │  Postgres + Row Level Security               │
                    │  SECURITY DEFINER RPCs (bootstrap_workspace, │
                    │    save_atc)                                 │
                    │  Admin client (bypass RLS for PAT ops,       │
                    │    invite token ops)                         │
                    └────────────────────┬─────────────────────────┘
                                         │ Postgres TCP
                    ┌────────────────────▼─────────────────────────┐
                    │             PERSISTENCE                      │
                    │  Supabase Postgres (hosted)                  │
                    │  No cache layer, no queue, no object storage │
                    └──────────────────────────────────────────────┘
```

| Component | Role | Persistence / Integrations | Why it matters for QA |
|---|---|---|---|
| `withApiHandler()` | Global error envelope, request-id injection, structured logging | None (wraps handlers) | All API errors must follow the envelope shape `{ error: { code, message } }`. Non-envelope errors = handler bug. |
| `requireAuth()` | Dual-mode auth — Bearer first, cookie second | `access_tokens`, `access_token_secrets` (admin client) | Any route using `requireAuth` must be tested with BOTH auth schemes. Priority: Bearer shadows cookie. |
| RLS (Supabase) | Workspace-scoped data isolation | All tenant tables | Data leakage between workspaces = RLS misconfiguration. QA must verify cross-workspace isolation. |
| SECURITY DEFINER RPCs | Atomic multi-table writes (workspace bootstrap, ATC save) | `workspaces`, `workspace_members`, `atcs`, `atc_steps`, etc. | Partial saves are impossible — success or full rollback. Test interruption / error paths. |
| Admin client | Bypasses RLS for PAT ops, invite secret ops | `access_token_secrets`, `workspace_invite_secrets` | QA roles CANNOT read these sibling tables — not a bug. Hash tables are intentionally opaque to analytics. |
| `idempotency_keys` | Replay-safe mutation support | DB table | `Idempotency-Key` header enables safe retries. Same key + different payload → 409. |

## 5. External Integrations

| Service | Trigger | Direction | Failure mode (user-visible) | Journeys affected |
|---|---|---|---|---|
| **Supabase Auth (OTP)** | `POST /api/v1/auth/magic-link` | Outbound sync | 429 (free tier: 4 OTP/hr/email) → `rate_limited` error; 5xx → `upstream_error` | Journey 1 (onboarding) |
| **Supabase Auth (OAuth)** | GET `/auth/callback?code=` | Outbound sync (provider callback) | Exchange failure → redirect to `/login?error=otp_exchange_failed` | Journey 1 (OAuth variant) |
| **Supabase Postgres (RLS)** | Every authenticated DB query | Internal (same service) | RLS policy miss → query returns 0 rows (silent 404) or 403 | All journeys |
| **Supabase Admin API** | PAT mint, user provisioning (`/auth/signup`), invite secret writes | Internal (service-role client, bypasses RLS) | Admin API down → 500 internal error on PAT/signup flows | Journey 2, Journey 5 |
| **Resend (email)** | _(Not yet wired in app code)_ | _(Planned outbound)_ | Currently: invite link only in API response + server console.log — user never gets an email | Journey 3 (invite) |

> **QA Note on Resend**: invite email delivery is absent from current implementation. Testing Journey 3 requires extracting `accept_url` from the `POST /api/v1/workspaces/{id}/invites` response body directly — no email interception needed.

> **QA Note on OTP rate limit**: Supabase free tier caps at 4 OTPs/hour/email. Test data strategy must account for this — use multiple test email addresses or prefer the headless signin/signup paths for automated suites.
