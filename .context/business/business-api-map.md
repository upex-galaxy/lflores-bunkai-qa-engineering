# Business API Map: Bunkai TMS

---

## 1. Executive Summary

Bunkai's API has two kinds of callers: human users navigating the browser app, and machine callers (CLI tools, AI agents, CI pipelines) consuming the REST layer directly. Both reach the same endpoints under `/api/v1/`, but through different auth schemes — browser users carry a Supabase session cookie while machine callers present a Bearer PAT (`bk_pat_*`). Every endpoint that touches workspace data is further bounded by Supabase Row Level Security, so a valid token only ever sees the workspaces it belongs to.

Since June, the product closed the loop: authoring (ATCs, Tests) now feeds real **execution** (Runs, with per-step results), execution feeds **defect tracking** (Bugs), and the whole chain — User Story → ATC → Test → Run → Bug — is queryable as a single **Traceability Report**. **ATC authoring is no longer split by caller type**: creation is REST-only for both browser and machine now (the browser's `NewAtcEditor` calls `fetch('/api/v1/atcs')` directly, same as a CLI would); editing uses a Server Action for the browser but calls the exact same `bunkai_update_atc` RPC the REST `PATCH` endpoint uses — unified behavior, not two divergent code paths as the June doc described.

The API is served as Next.js 15 Route Handlers running in Node.js. There is no separate API gateway. Multi-tenancy is enforced at the database layer (Supabase RLS) rather than at the handler layer. Every route now runs through a single unified gateway, `withApiHandler()` (`lib/api/handler.ts`), secure-by-default (`auth: 'required'` unless explicitly opted into `auth: 'public'`). **Two previously-open security bugs are now fixed**: BK-134/135 (`workspace:admin` PAT self-issuance) and BK-316 (Bearer callers ignoring the active-workspace switch) — see §2 and §7.

## 2. Permission & Auth Model

### Tier taxonomy

| Tier | Who it applies to | How to acquire | Where enforced (code path) |
|---|---|---|---|
| **Public** | Unauthenticated callers, bots, docs consumers | No token needed | `withApiHandler(handler, { auth: 'public' })` — only 8 routes use this explicit opt-out |
| **Cookie (Supabase Session)** | Browser users | OTP exchange at `GET /auth/callback` OR password sign-in via `POST /api/v1/auth/signin` OR BK-166 email/password + OTP confirm via `POST /api/v1/auth/confirm` | `lib/api/principal.ts` — identity resolution into a unified `Principal` type |
| **Bearer PAT** | CLI, AI agents, CI pipelines | `POST /api/v1/tokens` (session required) OR auto-minted by `POST /api/v1/auth/signin` / `.../signup` / `.../confirm` | `requireBearerToken()` in `lib/api/middleware/bearer.ts` → prefix lookup + hash compare |
| **RLS (DB-layer)** | Every DB query regardless of auth scheme | Implicit — Supabase applies it on every query | Supabase Postgres policies on all tables |

> **Architecture note (new since June)**: the old monolithic `lib/api/auth.ts` no longer exists — split into `lib/api/principal.ts` (identity + `Principal` type), `lib/api/handler.ts` (the `withApiHandler` gateway), `lib/api/user-jwt.ts` (mints a short-lived per-user JWT for PAT→RLS impersonation), and `lib/api/workspace-cookie.ts` (the `bk_active_ws` cookie). Functionally equivalent to June's `requireAuth()`, reorganized.

> **Scope model**: 4 scopes, unchanged since June: `atc:read`, `atc:write`, `run:execute`, `workspace:admin`. New: `DEFAULT_PAT_SCOPES` (excludes `workspace:admin`) is used for every auto-minted headless token (signin/signup/confirm) — a caller must explicitly go through `POST /api/v1/tokens` to ever get an admin-scoped PAT, and even then only if authorized (see fix below). Cookie sessions still have no scope concept — permission is RLS + role only.

> **✅ SECURITY GAP RESOLVED — BK-134/135**: `POST /api/v1/tokens` now calls `assertTokenIssuanceAuthorized()` (`lib/api/pat.ts:53-89`) **before** minting, requiring active membership for the target `workspace_id` and admin/owner role specifically for `workspace:admin` scope. `assertNoGlobalAdminScope()` additionally hard-rejects any global (`workspace_id=NULL`) admin-scoped token on headless issuance paths. A companion runtime gate, `assertWorkspaceContext()` (`lib/api/principal.ts:91-104`), binds an admin-scoped PAT to its issuing workspace at *call* time too — not just at mint time. **Residual risk**: the ~136 admin-scoped PATs minted on staging *before* this fix (confirmed present as of the June audit) were not confirmed revoked as part of the fix — see new Discovery Gap GAP-14.

### Token flow — Magic-link (primary browser path, unchanged shape)

```
Browser                 API                     Supabase Auth        DB
  |                      |                           |                 |
  |-- POST /api/v1/auth/magic-link {email} -------> |                 |
  |                      |-- signInWithOtp() ------> |                 |
  |<-- 200 { ok: true } -|                           |                 |
  |   [user clicks email link]                       |                 |
  |-- GET /auth/callback?code=<OTP> ---------------- |                 |
  |                      |-- exchangeCodeForSession() -> Supabase      |
  |<-- 302 → /projects --| (Supabase session cookies set)              |
```

**Still same-device only.** A BK-400 attempt to make this cross-device (swap to a `token_hash`-based, non-PKCE sender) was implemented then **explicitly reverted** in the same story as "the dangerous part" — the callback route can accept `token_hash`, but the send side is still PKCE. Do not test cross-device magic-link expecting it to work.

### Token flow — Password sign-in / BK-166 sign-up + OTP (machine + human headless path)

```
CLI / Agent / Browser        API                        Supabase Auth        DB
  |                           |                              |                 |
  |-- POST /auth/signin {email, password} ------------> |                 |    (existing user)
  |   OR: POST /auth/check-email → routes to signup      |                 |
  |       → POST /auth/signup {email, password}          |                 |    (new user, BK-166)
  |       → POST /auth/confirm {email, otp_code}          |                 |    (mandatory OTP, no bypass)
  |                           |-- signInWithPassword() / admin.createUser() |
  |                           |<-- { user, session } ---- |                 |
  |                           |-- mintPat(DEFAULT_PAT_SCOPES) ------------->|
  |<-- 200 { session, pat: { token: "bk_pat_..." } } ---------------- |    |
```

**Numbered narrative:**
1. `POST /api/v1/auth/check-email` routes the caller to sign-in or sign-up based on whether the email exists.
2. Existing user: `POST /api/v1/auth/signin` — email+password against Supabase Auth, mints a PAT inline.
3. New user (BK-166): `POST /api/v1/auth/signup` then a **mandatory** `POST /api/v1/auth/confirm` with a 6-digit OTP — no bypass exists, unlike June's `email_confirm: true` shortcut. `POST /api/v1/auth/resend` re-sends the code.
4. Every headless mint point (signin, confirm) uses `DEFAULT_PAT_SCOPES` — never `workspace:admin` by default.
5. Bearer verification unchanged: `token_prefix` O(1) lookup → hash compare → expiry/revocation check → `last_used_at` update.

### Journey 2 — Machine/CI sign-in + PAT lifecycle (BK-134/135 fixed)

**Business purpose**: A CLI tool or AI agent authenticates headlessly, gets a token, and can list/issue/revoke its own tokens for ongoing credential hygiene.

```
CLI / Agent        /api/v1/auth/signin          DB
  |-- POST {email, password} -------------------> |
  |<-- 200 { session, pat: {token, scopes: DEFAULT_PAT_SCOPES} }
  |                                                |
  |-- [later] POST /api/v1/tokens (Cookie auth, extra PAT)
  |   → assertTokenIssuanceAuthorized(): role+membership check
  |   → assertNoGlobalAdminScope(): blocks workspace_id=NULL + workspace:admin
  |<-- 201 { token, scopes } (or 403 if unauthorized for requested scope)
  |
  |-- GET /api/v1/tokens (Cookie auth) --> list own tokens (no secrets returned)
  |-- DELETE /api/v1/tokens/{id} --> revoked_at SET (soft, audit trail preserved)
```

**Numbered narrative:**
1. Initial token via headless signin/signup/confirm — `DEFAULT_PAT_SCOPES`, never admin.
2. Extra/scoped tokens via `POST /api/v1/tokens` — session-only (PATs cannot mint PATs, 403 `forbidden` if attempted via Bearer). Now role-gated for `workspace:admin` (BK-134/135 fix).
3. `assertWorkspaceContext()` re-checks the workspace binding on every subsequent admin-scoped call, not just at mint — an admin PAT cannot act outside its issuing workspace even if the underlying user administers others.
4. Revocation is soft (`revoked_at`), immediately enforced by the Bearer middleware, audit trail preserved.

**Endpoints involved**: `POST /api/v1/auth/{signin,signup,confirm}`, `GET/POST /api/v1/tokens`, `DELETE /api/v1/tokens/{id}`
**Entities touched**: `access_tokens`
**Feature IDs**: FEAT-002, FEAT-003, FEAT-005

### Journey 4 — ATC Authoring (browser + machine — now unified, corrected from June)

**Business purpose**: Author or edit an ATC (Atomic Test Component), anchored to a User Story + Acceptance Criterion. **June's doc described this as two structurally different journeys (4a browser-Server-Action-only, 4b machine-REST-only). This was accurate in June but is no longer true — the two paths converged.**

```
CREATE (browser AND machine — same REST endpoint now):
  Browser (NewAtcEditor.tsx) ──┐
                                ├──► POST /api/v1/atcs ──► bunkai_create_atc RPC
  CLI/Agent (Bearer, atc:write)┘        (SECURITY DEFINER, 1 transaction:
                                          atcs + atc_steps + atc_assertions +
                                          atc_acceptance_criteria)

EDIT (still two entry points, but ONE shared RPC underneath):
  Browser: saveAtcAction() Server Action ──┐
    (ifMatch = null — last-write-wins)     ├──► bunkai_update_atc RPC
  CLI/Agent: PATCH /api/v1/atcs/{id} ──────┘        (SECURITY DEFINER, same
    (X-If-Match required — optimistic lock)          full-replace semantics
                                                       for BOTH callers)
```

**Numbered narrative:**
1. **Creation is REST-only for everyone now.** `components/atcs/NewAtcEditor.tsx:206` calls `fetch('/api/v1/atcs', ...)` directly — the browser is just another REST client here, same as a CLI. `bunkai_create_atc` RPC does the atomic 4-table insert regardless of caller.
2. **Editing still has two entry points but they converge on one RPC.** The browser's edit path (`app/(app)/projects/[projectSlug]/atcs/[atcId]/actions.ts` → `saveAtcAction` Server Action) was explicitly rewritten (per its own in-code comment) to call the canonical `bunkai_update_atc` RPC — "the same path the headless `PATCH /api/v1/atcs/{id}` uses so a UI edit behaves identically to an API edit." The legacy `bunkai_save_atc` RPC this replaced never emitted the `atc.updated` event with real `affected_test_ids`, so UI edits used to be invisible to search reindex — that's fixed now too.
3. **One real remaining difference**: optimistic locking. The REST `PATCH` requires `X-If-Match: <version>` and 409s on mismatch. The browser Server Action passes `ifMatch: null` — last-write-wins UX, by design (single-user editing assumption), not a bug.
4. **`bunkai_save_atc` itself is now dead code** — retained in the DB (migration-frozen, never dropped) but called by nothing. See `business-data-map.md` §2 for the fuller correction of June's (wrong) claim that this RPC had been *removed*.
5. Anchoring invariant unchanged: every ATC requires ≥1 User Story + ≥1 Acceptance Criterion, enforced before either RPC runs.

**Endpoints involved**: `POST /api/v1/atcs`, `PATCH /api/v1/atcs/{id}` (REST); `saveAtcAction` (Server Action, browser edit only)
**Entities touched**: `atcs`, `atc_steps`, `atc_assertions`, `atc_acceptance_criteria`
**Feature IDs**: FEAT-016, FEAT-017, FEAT-018

### Journey 5 — Workspace switching (BK-316 fixed)

**Business purpose**: A member of multiple workspaces switches their active workspace context.

```
Browser (WorkspaceSwitcher) --POST /me/active-workspace {workspace_id}--> assertSessionOnly(): 403 if Bearer
                                                                          → RLS membership check → 403 if not member
                                                                          → set bk_active_ws httpOnly cookie
                                                                          ← 200 { id, slug, name, role }
```

**Numbered narrative:**
1. `assertSessionOnly()` (`app/api/v1/me/active-workspace/response.ts:42-49`) rejects Bearer/PAT callers with `403 forbidden` up front — fixed BK-316, commit `4914f7c`, 2026-08-07. This was a rejection fix, not a "make Bearer respect the switch" fix: a PAT's workspace binding is fixed at mint time by design.
2. Cookie-authenticated request continues: RLS membership check, `bk_active_ws` cookie set.
3. Bearer callers instead resolve their workspace per-request from `principal.workspaceId` (the PAT's own binding) — orthogonal to the cookie, always was.

**Endpoints involved**: `POST /api/v1/me/active-workspace`, `GET /api/v1/me`
**Entities touched**: `workspaces`, `workspace_members`, `access_tokens`
**Feature IDs**: FEAT-009, FEAT-006

> **QA regression check**: a Bearer/PAT request here must return 403, never 200 — a 200 is a BK-316 reintroduction (`app/api/v1/me/active-workspace/route.test.ts:15-31`).

### Journey 6 🆕 — Manual Run Execution (BK-182, shipped — was "planned" in June)

**Business purpose**: This is the feature that turns Bunkai from an authoring tool into a real closed-loop TMS — a QA engineer (or agent) actually executes a Test and records a per-step result. June's doc described this entire domain as DB-unmigrated and API-nonexistent; it is now fully live.

```
[Member/Agent] --POST /runs {test_id, environment_id}
                  header: Idempotency-Key (REQUIRED)
                  → 24h start_token dedup window (no double-start on retry)
                  → resolveRunWorkspaceId(): resolves workspace for Bearer
                    callers with no cookie (BK-182 — deliberately untouched
                    by the later BK-316 fix, per commit message: "throwing
                    there would revert the BK-182 fix")
                  → bunkai_create_run RPC → runs + run_atcs (ATC snapshot,
                    denormalized titles survive later ATC edits)
                  ← 201 { run_id, status: 'running' }

[Executor]      --POST /runs/{id}/steps/{stepId}/mark {status, evidence?}
[Executor]      --POST /runs/{id}/abort {abort_reason}   (DB CHECK constraint
                                                            enforces reason present)
[Executor]      --POST /runs/{id}/finish
                  → remaining pending steps auto-skipped
                  → DB trigger fires → notifications row (run.finished/aborted)

[QA Engineer]   --POST /bugs (from a failed step)
                  → bugs_check_consistency trigger validates run_step/atc/
                    run/project all agree before insert is allowed
```

**Endpoints involved**: `POST /api/v1/runs`, `.../abort`, `.../finish`, `.../steps/{id}/mark`, `POST /api/v1/bugs`
**Entities touched**: `runs`, `run_atcs`, `run_steps`, `bugs`
**Feature IDs**: FEAT-029 through FEAT-034 (Manual Execution domain), FEAT-046 (Bug Reporting)

| Component | Role | Why it matters for QA |
|---|---|---|
| `withApiHandler()` | Global error envelope, request-id, secure-by-default gateway | All API errors follow `{ error: { code, message } }`. Non-envelope errors = handler bug. |
| `lib/api/principal.ts` | Identity resolution — Bearer first, cookie second | Any route must be tested with BOTH auth schemes where both are valid. |
| `assertWorkspaceContext()` | Re-checks admin-PAT workspace binding on every call, not just mint | New since June (BK-134/135 fix) — test that an admin PAT genuinely cannot act cross-workspace. |
| RLS (Supabase) | Workspace-scoped data isolation | Data leakage between workspaces = RLS misconfiguration. Verify cross-workspace isolation on every new entity, especially the 8 new tables. |
| SECURITY DEFINER RPCs | Atomic multi-table writes | Partial saves impossible — success or full rollback. `bunkai_create_run` snapshots ATC titles atomically with run creation. |
| `bugs_check_consistency` trigger | DB-level integrity guard on bug filing | Verify it can't be bypassed with a crafted cross-run/cross-project payload — it's a trigger, not just app validation. |
| `idempotency_keys` | Replay-safe mutation support | Now live and load-bearing on `POST /runs` (24h dedup, required header) — was unwired/planned in June. |
