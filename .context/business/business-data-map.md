## 1. Executive Summary

Bunkai is a **Test Management System (TMS)** built on one non-negotiable structural rule: **every ATC must be anchored to a User Story AND at least one Acceptance Criterion**. Test cases are not free-form scripts — they are ordered chains of reusable ATCs, so editing one ATC cascades to every Test that chains it.

Since June, the product grew from an authoring-only tool (US/AC/ATC/Test CRUD, no execution) into a **closed-loop TMS**: ATCs chain into Tests, Tests execute as Runs with per-step pass/fail/blocked/skipped evidence, failed steps can raise a Bug, and the whole US→AC→ATC→Run→Bug chain is queryable as a single traceability report. In-app Notifications and Milestones round out the workflow layer.

Two editions are described in architecture docs — **Bunkai Cloud** (Supabase Postgres, MVP) and **Bunkai Community** (self-hosted, Docker Compose) — but this update found **no code evidence of the Community/self-hosted path being implemented** (no object-storage SDK, no alternate DB adapter). Treat "one codebase, two editions" as a stated design goal, not a verified-shipped fact — same caution warranted for the Sentry/PostHog claim above.

### Correction: `bunkai_save_atc` RPC was never removed

June's doc stated the RPC was removed and ATC creation became an app-layer transaction, framing this as a QA atomicity risk. **This was incorrect.** The RPC still exists (`supabase/migrations/0007_save_atc.sql`) and is explicitly retained per a later migration comment (`0065_atc_tags_cap_guard.sql:15`). ATC creation and editing route through `bunkai_create_atc` / `bunkai_update_atc` SECURITY DEFINER RPCs — DB-layer transactional atomicity, same guarantee as always. The June-era "test for partial failure / orphan atc_steps" recommendation does not apply; that risk was never real.

### Flow 6: ATC Edit (Full Replace, RPC + optimistic lock)

```
[Member] ─► PATCH /api/v1/atcs/{id}
             header: X-If-Match (optimistic lock)
             body: {title?, steps?[], assertions?[], ac_ids?[], tags?}
             → supabase.rpc('bunkai_update_atc', {...})
             → PUT-style full replace: omitted children are CLEARED
             → user_story_id, module_id, slug IMMUTABLE
             → version++, emits atc.updated
             → returns affected_test_count (BK-21 — how many Tests
               chain this ATC and are therefore impacted by the edit)
```

**New since June**: `X-If-Match` optimistic locking (reject stale edits) and `affected_test_count` in the response (Test builder is live now, so this is no longer always 0).

### Flow 8: Bearer PAT Issuance + Auth (BK-134/135 fixed)

```
[User session] ─► POST /api/v1/tokens
```

```
[Any member] ─► GET /api/v1/projects/{id}/traceability?story={userStoryId}
```

### Flow 10 🆕: Manual Run Execution (BK-182)

```
[Member/Agent] ─► POST /api/v1/runs
                   header: Idempotency-Key (REQUIRED)
                   body: {test_id, environment_id}
                   → domain-level start_token, 24h dedup window
                     (prevents double-start on retry/double-click)
                   → resolveRunWorkspaceId(): for Bearer callers with
                     no active-workspace cookie, resolves the run's
                     workspace from the PAT's own binding (BK-182 fix —
                     deliberately NOT touched by the later BK-316 fix,
                     per commit message: "throwing there would revert
                     the BK-182 fix")
                   → supabase.rpc('bunkai_create_run', ...)
                   → runs INSERT (status='running')
                   → run_atcs INSERT (snapshot of each chained ATC —
                     denormalized title, survives later ATC edits)

[Executor]     ─► POST /api/v1/runs/{id}/steps/{stepId}/mark
                   body: {status: passed|failed|blocked|skipped, evidence?}
                   → run_steps UPDATE

[Executor]     ─► POST /api/v1/runs/{id}/abort   (requires abort_reason)
               ─► POST /api/v1/runs/{id}/finish
                   → runs.status SET; remaining pending steps auto-skipped
                   → trigger fires → notifications INSERT for
                     run.finished / run.aborted events

[QA Engineer]  ─► on a failed run_step, file a Bug
                   → POST .../bugs — trigger bugs_check_consistency
                     validates the run_step/atc/run/project all agree
                     before the insert is allowed
```

**Business purpose**: this is the feature that turns Bunkai from "test case authoring tool" into a real TMS — someone actually executes the Tests and the result is recorded per-step, not just per-ATC. **Business rule**: `runs` itself is deliberately excluded from the Realtime publication (only `run_atcs`/`run_steps` broadcast) — the parent row's status is derived, not the primary live-update signal.

## 7. Multi-tenancy + RLS

RLS policy pattern (per-table `workspace_id` membership check) — **not re-queried this round**, carried forward from June unchanged since it's a foundational, low-churn pattern. Role hierarchy (`viewer ⊂ member ⊂ admin ⊂ owner`) and PAT scopes (`atc:read`/`atc:write`/`run:execute`/`workspace:admin`) also carried forward, **with one addition**: `workspace:admin`-scoped PATs are now also bound to their issuing workspace at the application layer (`assertWorkspaceContext`, BK-134/135 fix) — this is an *additional* enforcement layer on top of RLS, not a replacement for it. A PAT that somehow bypassed this app-layer check would still be stopped by RLS underneath.

**QA Critical (unchanged)**: RLS failures are invisible at the application layer (row simply not returned, not a 403). Cross-workspace data leaks require specific test cases that verify isolation — not just happy-path access.
