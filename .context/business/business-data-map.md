## 1. Executive Summary

Bunkai is a **Test Management System (TMS)** built on one non-negotiable structural rule: **every ATC must be anchored to a User Story AND at least one Acceptance Criterion**. Test cases are not free-form scripts — they are ordered chains of reusable ATCs, so editing one ATC propagates to every Test that chains it.

Two editions ship from one codebase: **Bunkai Cloud** (Supabase Postgres, MVP) and **Bunkai Community** (self-hosted Docker Compose, Phase 2). Data model is identical across editions.

### Key Relationships (QA perspective)

**The structural rule enforced at DB layer via `bunkai_save_atc` RPC:**
```
bunkai_save_atc(p_user_story_id, p_layer, p_steps, p_assertions, p_ac_ids, ...)
  → single transaction:
     INSERT atcs
     INSERT atc_steps[]
     INSERT atc_assertions[]
     INSERT atc_acceptance_criteria[] (≥1 required)
```
The RLS policies + this RPC together prevent orphan ATCs at the constraint layer, not the application layer.

**Modules tree via self-referential FK:**
- `modules.parent_module_id` → `modules.id` (nullable for root modules)
- `modules.path` is materialized (e.g. `/Payment/Refunds`) — breadcrumbs without recursion
- `modules.position` enables sibling ordering within a parent

## 3. Business Flows

### Flow 1: Workspace Setup + First Login

```
User ─► /auth/sign-in ─► Next.js middleware ─► Supabase Auth (OAuth GitHub/Google)
                                                       │
                          OR: POST /api/auth/magic-link → magic_link_tokens INSERT
                              User clicks email link  → magic_link_tokens.consumed_at SET
                                                       │
                                                       ▼
                                              auth.users row (Supabase managed)
                                                       │
                                                       ▼
                                    bunkai_bootstrap_workspace(p_name, p_slug)
                                    [Supabase RPC — first verified login only]
                                                       │
                                             ┌─────────┴──────────┐
                                             ▼                    ▼
                                         workspaces         workspace_members
                                         row created         (role=owner)
```

**Business Rules:**
- First verified login → workspace auto-bootstrapped via `bunkai_bootstrap_workspace` RPC
- Invite path: `workspace_invites` row consumed on acceptance → `workspace_members` row created
- Magic link is **custom implementation** (not Supabase's built-in magic link) — `magic_link_token_secrets.token_hash` + `ip_hash` for security pinning

**QA Risk:** Custom magic link bypasses Supabase Auth's built-in flow — expiry, single-use consumption, and IP binding are all app-layer logic, not platform-enforced.

### Flow 2: Project + Module Hierarchy Setup (BK-9 RELEVANT)

```
[QA Lead] ─► POST /api/v1/projects ──────► projects row (workspace_id, slug unique)
                │
                ├─► POST /api/v1/modules ─► modules row
                │     body: {name, project_id, parent_module_id?}
                │                │
                │                ▼
                │   path computed: parent.path + "/" + slug(name)
                │   position: last sibling + 1
                │
                ├─► POST /api/v1/modules (child) ─► parent_module_id = above
                │     depth check: count ancestors via recursive CTE
                │     depth 5 → warn (non-blocking)
                │     depth 7 → reject (HTTP 422)
                │
                └─► GET /api/v1/projects/{id}/tree
                      recursive CTE on modules
                      returns: {id, name, path, position, children:[...]}
```

**Business Rules for Modules (BK-9 ACs):**
- `name` min 2 chars (AC-3: "P" rejected)
- Nesting depth: soft warning at level 5, hard block at level 7 (AC-4 and AC-5)
- `path` is materialized on insert/update — breadcrumb reads are O(1)
- Root module: `parent_module_id = null`
- `position` enables manual reordering among siblings

**QA Note on BK-9:** This flow is the direct subject of BK-9. The `modules` table IS in the live DB — this feature is testable today.

### Flow 3: ATC Creation (Transactional)

```
[QA Engineer] ─► select Module + US + AC ─► ATC Editor
                      │
                      ▼
               POST /api/v1/atcs
               body: {module_id, user_story_id, layer, title,
                      steps:[], assertions:[], ac_ids:[]}
                      │
                      ▼
               bunkai_save_atc RPC (single transaction):
                 INSERT atcs (layer required)
                 INSERT atc_steps[] (ordered by position)
                 INSERT atc_assertions[] (ordered by position)
                 INSERT atc_acceptance_criteria[] (≥1 required)
                 INSERT activity_log
                      │
                      ▼
               Supabase Realtime broadcast → subscribed clients refresh tree
```

**Business Rules:**
- `layer` ∈ {UI, API, Unit} — mandatory, save disabled until set
- `user_story_id` mandatory (FK constraint)
- `atc_acceptance_criteria` ≥1 row required (enforced by RPC logic)
- ATC `slug` = `{module-slug}/{atc-id-padded}` — auto-computed
- `version` field tracks edits — "one-edit-many-tests" relies on this

### Flow 4: Bearer PAT Issuance + Auth

```
[Admin] ─► POST /api/v1/auth/tokens ─► access_tokens INSERT (scopes, expires_at)
                                        access_token_secrets INSERT (hash)
                                                │
                                         plain token returned ONCE
                                         (SHA-256 hash stored, plain never persisted)

[Agent] ─► Authorization: Bearer bk_pat_... ─► middleware.ts
                                                  │
                                                  ▼
                                         SHA-256 hash lookup in access_token_secrets
                                         verify: expires_at > now() AND revoked_at IS NULL
                                         UPDATE access_tokens.last_used_at = now()
                                                  │
                                          attach {user_id, workspace_id, scopes}
                                          to request context
```

**Business Rules:**
- Plain token returned ONCE on issuance — loss requires revoke + re-issue
- Hash stored in separate `access_token_secrets` table (not on `access_tokens` row)
- `last_used_at` updated on every authenticated request
- `workspace_id` nullable — token can be workspace-scoped or global

## 7. Multi-tenancy + RLS

**Policy pattern** (every table with `workspace_id`):

```sql
USING (
  EXISTS (
    SELECT 1 FROM workspace_members wm
    WHERE wm.workspace_id = <table>.workspace_id
      AND wm.user_id      = auth.uid()
      AND wm.status       = 'active'
  )
)
```

**Role hierarchy** (`viewer ⊂ member ⊂ admin ⊂ owner`):

| Role | Capabilities |
|---|---|
| `viewer` | Read-only across every workspace table |
| `member` | Full CRUD on Project entities (Modules, US, AC, ATC) |
| `admin` | + manages members, integrations, access tokens |
| `owner` | + workspace deletion, billing |

**PAT scopes are an additional restriction on top of role.** A `member` can mint a read-only PAT — that bearer cannot create ATCs even though the underlying user can.

**QA Critical:** RLS failures are invisible at the application layer (row simply not returned, not a 403). Cross-workspace data leaks require specific test cases that verify isolation — not just happy-path access.
