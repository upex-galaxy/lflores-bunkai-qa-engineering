## 1. Executive Summary

Bunkai is a **Test Management System (TMS)** built on one non-negotiable structural rule: **every ATC must be anchored to a User Story AND at least one Acceptance Criterion**. Test cases are not free-form scripts — they are ordered chains of reusable ATCs, so editing one ATC cascades to every Test that chains it.

Two editions ship from one codebase: **Bunkai Cloud** (Supabase Postgres, MVP) and **Bunkai Community** (self-hosted Docker Compose, Phase 2). Data model is identical across editions.

### Key Architectural Change: bunkai_save_atc RPC Removed

**Previous (before 2026-06-13)**: ATC creation routed through a `bunkai_save_atc` SECURITY DEFINER RPC — single DB-layer transaction enforced atomicity.

**Current**: Only 2 DB functions exist (`bunkai_atcs_refresh_tsv` trigger, `bunkai_set_updated_at` trigger). ATC creation now handled entirely in the Next.js route handler for `POST /api/v1/atcs` — app-layer transaction via Supabase client.

**QA Risk**: Atomicity guarantee is now app-layer, not DB-layer. A crash mid-request could leave orphan `atc_steps` without a parent `atcs` row. Test for partial failure scenarios.

## 3. Business Flows

### Flow 1: Workspace Setup + First Login

```
User ─► /auth/sign-in ─► Next.js middleware ─► Supabase Auth (OAuth GitHub/Google)
                                                       │
                          OR: POST /api/v1/auth/magic-link → magic_link_tokens INSERT
                              User clicks email link  → magic_link_tokens.consumed_at SET
                                                       │
                          OR (CLI/QA): POST /api/v1/auth/signin (password)
                                       POST /api/v1/auth/signup (provision + PAT)
                                                       │
                                                       ▼
                                              auth.users row (Supabase managed)
                                                       │
                                                       ▼
                                    POST /api/v1/workspaces
                                    → bunkai_bootstrap_workspace RPC (owner row)
                                                       │
                                             ┌─────────┴──────────┐
                                             ▼                    ▼
                                         workspaces         workspace_members
                                         row created         (role=owner)
```

**Business Rules:**
- First login → workspace auto-bootstrapped (first-time) or manual via `POST /api/v1/workspaces`
- Invite path: admin issues invite → `workspace_invites` row → user accepts via `POST /api/v1/invites/accept` → `workspace_members` row
- **NEW**: Headless `signin` + `signup` endpoints for CLI/agent/QA use — `signup` uses `email_confirm: true` to skip email verification
- Magic link is **custom implementation** — expiry, single-use, not platform-enforced

**QA Risk:** Two auth paths (OAuth + custom magic link) + two headless paths — four separate session creation code paths, each with different failure modes.

### Flow 2: Invite Lifecycle (Full CRUD)

```
[Admin] ──► POST /api/v1/workspaces/{id}/invites
             body: {email, role}
             → workspace_invites INSERT (expires_at = now() + 7 days)
             → returns {id, token, accept_url} — token returned once, not emailed
                    │
                    ├──► POST /api/v1/workspaces/{id}/invites/{inviteId}  (rotate)
                    │     → new secret + expires_at extended 7 days
                    │     → clears prior accepted_at / revoked_at
                    │
                    ├──► DELETE /api/v1/workspaces/{id}/invites/{inviteId}  (revoke)
                    │     → revoked_at SET
                    │
                    └──► POST /api/v1/invites/accept  (recipient)
                          → validates: caller.email == invite.email
                          → validates: not expired, not revoked
                          → workspace_members INSERT (role from invite)
                          → invite.accepted_at SET
```

**Business Rules:**
- Token shared out-of-band (MVP does NOT send email)
- Admin/owner only to issue, rotate, revoke
- Accept requires caller's email to match invite email
- Rotate extends expiry AND resets acceptance/revocation state

### Flow 3: Project + Module Hierarchy (Full CRUD)

```
[Member] ─► POST /api/v1/workspaces/{id}/projects
             → projects row (workspace_id, slug auto-derived from name)
                    │
                    ├─► POST /api/v1/projects/{id}/modules
                    │     body: {name, parent_module_id?}
                    │     → path computed: parent.path + "/" + slug(name)
                    │     → position: last sibling + 1
                    │     → depth >= 5 → 200 + soft warning flag
                    │     → depth > 6  → 422 rejected
                    │
                    ├─► PATCH /api/v1/modules/{id}
                    │     rename: rebuilds path + ALL descendant paths
                    │     move:   parent_module_id change → subtree relocated
                    │             cycle check → 422
                    │             depth overflow → 422
                    │             sibling slug collision → 409
                    │
                    └─► DELETE /api/v1/modules/{id}
                          → modules.archived_at SET (soft delete)
                          → cascade: descendant modules + user_stories
                            + acceptance_criteria + ATCs archived
                          → returns {modules_count, stories_count,
                                     criteria_count, atcs_count}
                          → already-archived → 409
```

**Business Rules:**
- Module name min 2 chars; soft warn at depth 5, hard block at depth > 6
- `path` is materialized — breadcrumb reads O(1), no recursive join at read time
- Archive is cascading — one DELETE archives the whole subtree atomically

### Flow 4: User Story + Acceptance Criteria (Full CRUD)

```
[Member] ─► POST /api/v1/modules/{id}/user-stories
             body: {title (3-200 chars), description?, external_id?}
             → user_stories INSERT (status='draft', module_id, project_id)
             → 409 on duplicate Jira key within project
                    │
                    ├─► POST /api/v1/user-stories/{id}/acceptance-criteria
                    │     body: {title, description?, position?}
                    │     → acceptance_criteria INSERT at given position
                    │     → sibling positions gap-free (atomic shift)
                    │
                    ├─► PATCH /api/v1/acceptance-criteria/{id}
                    │     edit title/detail OR reposition (atomic, gap-free re-number)
                    │
                    └─► DELETE /api/v1/acceptance-criteria/{id}
                          → archived_at SET
                          → position gap closed
                          → if last active AC: story status reverted
                            (event: user_story_reverted)

[Member] ─► PATCH /api/v1/user-stories/{id}
             title / description / external_id
             → external_id immutable once set → 409 on change attempt

[Member] ─► DELETE /api/v1/user-stories/{id}
             → user_stories.archived_at SET
```

**Business Rules:**
- US title: 3–200 chars
- Jira key (`external_id`) immutable once set
- Deleting last AC triggers `user_story_reverted` event (status implication)
- `user_stories.status` = `'draft'` by default — additional states TBD (see Discovery Gaps)

### Flow 5: ATC Creation (App-Layer Transaction)

```
[Member] ─► POST /api/v1/atcs
             body: {module_id, user_story_id, layer,
                    title, steps:[], assertions:[], ac_ids:[]}
             → validates: every ac_id belongs to user_story_id
             → validates: module_id is US's module or descendant in same project
             → app-layer transaction (Next.js route handler):
                 INSERT atcs (layer req, status='unrun', version=1)
                 INSERT atc_steps[] (ordered by position)
                 INSERT atc_assertions[] (ordered by position)
                 INSERT atc_acceptance_criteria[] (≥1 required)
             → emits: atc.created event
             → Supabase Realtime broadcast → subscribed clients refresh
```

**Architecture Note:** `bunkai_save_atc` RPC removed. Transaction is now app-layer in Next.js. Atomicity guarantee is weaker — partial failures possible on infra outage mid-request.

### Flow 7: Jira Import

```
[Member] ─► POST /api/v1/imports
             body: {project_id, jql}
             → validates: at most one active import per project → 409 if running
             → import_jobs INSERT (status='queued', jql stored)
             → returns {id} immediately (async — does NOT block)
                    │
                    │ (background worker polls / runs)
                    │
                    ▼
            import_jobs: status = 'running', started_at SET
                    │
                    │ for each Jira issue page (next_page_token tracked):
                    │   upsert user_stories by external_id
                    │   created_count / updated_count / skipped_count incremented
                    │   errors[] appended on per-issue failures
                    │
                    ▼
            import_jobs: status = 'completed' | 'failed', completed_at SET

[Member] ─► GET /api/v1/imports/{id}
             → returns: status + per-run counts + per-issue errors
             (polling endpoint — client polls until status terminal)
```

**Business Rules:**
- Idempotent on re-run (dedup by `external_id`)
- At most one active import per project
- Errors are per-issue, not job-level — partial success possible

### Flow 8: Bearer PAT Issuance + Auth

```
[User session] ─► POST /api/v1/tokens
                   body: {name?, scopes[], expires_at?}
                   → access_tokens INSERT (token_prefix stored)
                   → plain secret returned ONCE
                   → hash stored (location: see Discovery Gaps NEW-G1)

[Agent] ─► Authorization: Bearer bk_pat_... ─► Next.js middleware
             → token_prefix extracted (first 12 chars) → O(1) index lookup
             → hash compare against stored hash
             → verify: expires_at > now() AND revoked_at IS NULL
             → UPDATE access_tokens.last_used_at = now()
             → attach {user_id, workspace_id, scopes} to request context

[User] ─► DELETE /api/v1/tokens/{id}
           → revoked_at SET (soft delete — row stays in audit trail)
```

**Scopes** (from `access_tokens.scopes` column description): `atc:read`, `atc:write`, `run:execute`, `workspace:admin`

```
       ├──► expired   (now() > expires_at — app-layer check)
       │
       ├──► revoked   (DELETE /api/v1/workspaces/{id}/invites/{inviteId} → revoked_at SET)
       │
       └──► rotated   (POST /api/v1/workspaces/{id}/invites/{inviteId}
                        → new secret + expiry reset + accepted_at/revoked_at cleared)
```

### 4.6 `access_tokens`

```
active ──► revoked   (DELETE /api/v1/tokens/{id} → revoked_at SET)
      │
      └──► expired   (now() > expires_at)
```

### 4.7 `import_jobs`

```
queued ──► running ──► completed
                  └──► failed
```

**Notes:** At most one active (`queued` or `running`) import per project. `next_page_token` tracks Jira pagination cursor for resumable large imports.

## 7. Multi-tenancy + RLS

**Policy pattern** (every table with `workspace_id`):

```sql
USING (
  EXISTS (
    SELECT 1 FROM workspace_members wm
    WHERE wm.workspace_id = <table>.workspace_id
      AND wm.user_id      = auth.uid()
      AND wm.status       = 'active'
  )
)
```

**Role hierarchy** (`viewer ⊂ member ⊂ admin ⊂ owner`):

| Role | Capabilities |
|---|---|
| `viewer` | Read-only across every workspace table |
| `member` | Full CRUD on Project entities (Modules, US, AC, ATC); create projects |
| `admin` | + manages members, invites, access tokens |
| `owner` | + workspace deletion, billing, workspace rename |

**PAT scopes** (additional restriction on top of role): `atc:read`, `atc:write`, `run:execute`, `workspace:admin`. A `member` can mint a read-only `atc:read` PAT — that bearer cannot create ATCs even though the underlying user can.

**QA Critical:** RLS failures are invisible at the application layer (row simply not returned, not a 403). Cross-workspace data leaks require specific test cases that verify isolation — not just happy-path access.
