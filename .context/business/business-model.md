## 1. Problem Statement

Test Management Systems on the market today (Xray, Zephyr Scale, TestRail, qTest) are, in the target team's own framing, "document vaults with execution glued on top": each test case is a monolithic blob of free-form steps stored in a folder, with no structural enforcement.

Source: `upex-bunkai-tms/.context/PRD/executive-summary.md:12-19` (Problem Statement — "Steps are duplicated across dozens of tests... Traceability between User Story, Acceptance Criterion, Test, Run, and Bug is 'a free-text field if you remember to fill it'... Reports show '80% passing' without telling anybody what those 80% actually validate... Bugs are delegated to Jira the moment something fails... Regulated industries... cannot put their test data into a third-party SaaS").

This is corroborated by shipped code, not just stated intent: `bunkai-qa-engineering/.context/business/business-data-map.md:60` confirms the actual data-model rule this problem statement motivates — "every ATC must be anchored to a User Story AND at least one Acceptance Criterion" — is a real, enforced constraint (validated before the `bunkai_create_atc`/`bunkai_update_atc` SECURITY DEFINER RPCs run), not aspirational copy. The traceability-chain report (`GET /api/v1/projects/{id}/traceability`, shipped BK-45/48/50) is a direct, working answer to "nobody can answer 'what does this story cover?' with certainty" — see `business-data-map.md` Flow 9 and `business-api-map.md` Journey 7.

## 4. QA Relevance

| Business aspect | Testing implication |
|---|---|
| Structural traceability (US→AC→ATC mandatory anchoring) is THE core value prop, and it's DB-enforced | Every regression pass should include a negative test attempting to create an ATC without a US/AC — this is the product's central promise, worth a permanent smoke-test slot, not just a one-time check |
| Three customer segments include regulated-industry buyers who need self-hosted deployment | This is currently **unshippable and untestable** — do not schedule test effort against self-hosted/Community-edition scenarios; they don't exist yet |
| Revenue streams (Cloud subscription, Enterprise license) are unimplemented | No payment/subscription-gating logic exists to test yet; if a ticket references "Enterprise-only" or "paywall" behavior, treat it as a Discovery Gap requiring clarification before writing test cases, not an assumed AC |
| "One-edit-many-tests" (ATC reuse) is a headline value prop with a concrete, testable mechanism | `affected_test_count` on ATC edit responses is a direct, automatable regression check tying business value to a specific API field — see `business-api-map.md` Journey 4 |
| Agentic/AI-operator consumption is a first-class design goal (Persona "Karim" in the target's own `user-personas.md`) | Bearer PAT auth, idempotency keys, and predictable response envelopes are not incidental API hygiene — they're load-bearing for a stated customer segment (AI agents/CI). BK-134/135 and BK-316 (both fixed) were security regressions in exactly this surface — prioritize accordingly, consistent with `master-test-plan.md` §1 marking PAT issuance CRITICAL |
| Observability (Sentry/PostHog) is claimed in architecture docs but not implemented | QA sessions cannot rely on error-tracking tooling to catch failures automatically — manual repro / app logs are the only diagnostic path today |
| No CI/CD in the target repo (see `CLAUDE.md` Project Assessment, HIGH risk) | Regression suites in this QA-engineering repo cannot currently be triggered by a target-repo merge event; runs must be manually scheduled against `staging` |
