## Environment Variables

> Classified against `lib/env.ts` (the app-runtime Zod schema — server-only, throws at boot on validation failure) cross-checked with `.env.example` and the `process.env.*` grep across `app/`, `lib/`, `middleware.ts`, `scripts/`.

### ⚠️ Critical finding — `.env.example` does not document the exact names the app runtime requires

`lib/env.ts`'s `EnvSchema` (the module every server-only import relies on to boot) requires **`NEXT_PUBLIC_SUPABASE_ANON_KEY`** and **`SUPABASE_SERVICE_ROLE_KEY`** — but `.env.example` only documents the new-style pair, **`SUPABASE_PUBLISHABLE_KEY`** / **`SUPABASE_SECRET_KEY`**, which no app-runtime code reads (confirmed: zero matches for either name outside `.env.example` and `.mcp.json`/`opencode.jsonc`/tooling). `middleware.ts` and `lib/supabase/client.ts` independently read the same legacy `NEXT_PUBLIC_SUPABASE_ANON_KEY` name directly via `process.env.*`.

This is **confirmed intentional, not a bug** — per a maintainer comment in `cli/lib/variables-manifest.ts`: Supabase provisions the legacy pair (`SUPABASE_ANON_KEY`/`NEXT_PUBLIC_SUPABASE_ANON_KEY`/`SUPABASE_SERVICE_ROLE_KEY`) alongside the new pair simultaneously, both remain valid "until the end of 2026," and the Vercel↔Supabase integration provisions both automatically. But a first-time contributor copying `.env.example` literally and filling only the documented names will hit `lib/env.ts`'s Zod validation error at boot, because the legacy names it actually requires are never mentioned in `.env.example` by name. Flagged in Discovery Gaps below.

### Required (app will not start without these — `lib/env.ts` `EnvSchema`, no default)

| Variable | Format | Purpose |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | `https://<project-ref>.supabase.co` | Supabase project URL — client + server |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | opaque string (browser-safe, RLS-scoped) | Anon/publishable key — **not the same var name as `.env.example`'s `SUPABASE_PUBLISHABLE_KEY`**, see finding above |
| `SUPABASE_SERVICE_ROLE_KEY` | opaque string (server-only, bypasses RLS) | Admin client (`lib/supabase/admin.ts`) — **not the same var name as `.env.example`'s `SUPABASE_SECRET_KEY`**, see finding above |

## Local Development Setup

> No local Postgres — this recipe runs the Next.js app locally against a **remote** Supabase project (your own, or a shared `staging` one you have credentials for). Copy-pasteable end to end.

```bash
# 1. Clone (read-only reference — do not run against this from the QA repo directly)
git clone https://github.com/upex-galaxy/upex-bunkai-tms.git
cd upex-bunkai-tms

# 2. Install dependencies (Bun required — no npm/yarn/pnpm lockfile exists)
bun install

# 3. Set up environment
cp .env.example .env
# Edit .env — .env.example documents these (fill from Supabase Dashboard → Settings → API,
# or "Copy Snippet" from the Vercel Project Storage integration page):
#   NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
#   SUPABASE_PUBLISHABLE_KEY=<publishable key>
#   SUPABASE_SECRET_KEY=<secret key>
#   NEXT_PUBLIC_APP_URL=http://localhost:3000
#
# ⚠️ ALSO REQUIRED — NOT in .env.example by these names (see the ⚠️ finding above):
# the app runtime (lib/env.ts) validates and needs these LEGACY-named vars too,
# with the SAME underlying Supabase credential values:
#   NEXT_PUBLIC_SUPABASE_ANON_KEY=<same value as your publishable/anon key>
#   SUPABASE_SERVICE_ROLE_KEY=<same value as your secret/service_role key>
# (Both key pairs are valid simultaneously on a modern Supabase project — see
# Discovery Gaps for why this dual-naming exists.)

# 4. No local DB setup step — schema already exists on the remote Supabase project
#    you pointed at in step 3. No seed command exists.

# 5. Start the dev server (Webpack, not Turbopack — no --turbo flag in the script)
bun run dev

# 6. Verify
curl http://localhost:3000/api/v1/health
# Expect: {"ok":true,"service":"bunkai-tms","env":"local","ts":"..."}
```
