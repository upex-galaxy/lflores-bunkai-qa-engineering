## Routing + State + Auth Integration Points

> This section is consumed by `/adapt-framework` when wiring KATA fixtures to this stack — precision matters here.

### Routing

- **Next.js 15 App Router exclusively** — confirmed no `pages/` directory anywhere in the repo. Route groups: `(app)` (protected — `home/`, `projects/`, `onboarding/`, `settings/`, `workspaces/`, `activity/`) and `(auth)` (public — `login/`).
- `typedRoutes: true` — route links are compile-time type-checked (`next.config.ts`).
- Route protection is edge-middleware-based, not per-page: `middleware.ts` `PROTECTED_PREFIXES = ['/home', '/projects', '/onboarding', '/settings', '/activity']`, unauthenticated access redirects to `/login?next=<original-path>`.

### State management — **Phase 2 PRD Discovery Gap RESOLVED**

`.context/PRD/` flagged frontend state management as "not confirmed from `package.json` alone." Resolved this pass by reading component source directly:

- **No external state-management library** — confirmed by dependency grep: no Redux, Zustand, Jotai, Recoil, Valtio, or MobX in `package.json` `dependencies`/`devDependencies`.
- **Pattern in use: scoped React Context + local `useState` + URL-driven state**, idiomatic for App Router:
  - `components/providers/auth-context.tsx` — `AuthProvider`/`useAuth()`, wraps Supabase `getSession()` + `onAuthStateChange()`, exposes `{ user, session, loading, signInWithMagicLink, signOut }` app-wide.
  - `app/(app)/projects/[projectSlug]/workbench-context.tsx` — `WorkbenchProvider`, scoped to the project workbench subtree; holds ephemeral client state (open editor tabs) that survives child-route navigation because the layout stays mounted, while the *active* tab is derived from the URL (route-driven, not stored in Context) — explicit design comment in the file confirms this split.
  - `useSearchParams` (Next.js hook, not a library) drives login-flow state across 4 files under `app/(auth)/login/`.
- **Data fetching**: no TanStack Query / SWR / Apollo / RTK Query found — plain `fetch()` from Client/Server Components to the same-origin `/api/v1/**` REST surface (confirmed in `architecture.md` §3 Container diagram: `webUi → routeHandlers, fetch()`).

### Auth client integration

- **Supabase Auth (`@supabase/ssr` + `@supabase/supabase-js`)**, three integration surfaces:
  - `middleware.ts` — edge-layer `createServerClient()` + `supabase.auth.getUser()` on every request matching the route matcher; refreshes the session cookie before any route logic runs (explicit "do not run logic between createServerClient and getUser" comment in the file).
  - `lib/supabase/client.ts` — browser client (anon key), used by `AuthProvider`.
  - `lib/supabase/server.ts` / `lib/supabase/admin.ts` — SSR and service-role server clients respectively.
  - `components/providers/auth-context.tsx` — the React-facing `useAuth()` hook; subscribes to `onAuthStateChange` for multi-tab/multi-device sign-out propagation (uses a **hard navigation**, not `router.replace()`/`push()`, per an explicit BK-176 code comment — a gotcha worth knowing before writing an auth-flow E2E test that expects a soft navigation).
  - Dual auth scheme exists (cookie session for browser, Bearer PAT for machine callers) — already fully documented in `architecture.md` §8 Security Architecture, not duplicated here.

### Test-ID strategy

- **`data-testid` confirmed as the primary test-hook convention** — 48 of 64 `.tsx` files under `components/` (75%) reference `data-testid`. No `data-cy` or other convention found. This should be the default locator strategy for any Playwright/KATA Page component built against this app.
