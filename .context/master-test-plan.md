## 1. Executive Risk Map

Bunkai's fragility is concentrated in two layers: **identity + multi-tenancy** (if auth or RLS breaks, every single feature becomes unsafe or inaccessible) and **the ATC authoring + run execution pipeline** (if that breaks, the core product value disappears entirely). A third area — external integrations, especially async workers — fails silently and rots data without visible feedback, making it systematically under-tested.

The system is greenfield, so every flow carries elevated breakage likelihood. Priority is driven by **blast radius** (how many users and downstream flows break) and **irreversibility** (can it be rolled back without data loss?).

| Priority | Flow | Why it matters | Depends on / Affects |
|---|---|---|---|
| CRITICAL | Auth — OAuth + magic-link | Security gateway; every feature is behind auth | Workspace creation, RLS policies, JWT cookie |
| CRITICAL | Bearer PAT — issuance + scope enforcement | AI agents + CI use this exclusively; wrong scope = privilege escalation | All headless-mode flows |
| CRITICAL | RLS multi-tenancy — workspace isolation | A tenant seeing another tenant's data is a catastrophic breach | Every entity with `workspace_id` |
| CRITICAL | ATC create (transactional) | Core product value: structural traceability enforced at DB layer | US + AC must exist first; orphan ATCs rejected at constraint layer |
| HIGH | Run lifecycle — start → step result → finish/abort | Execution correctness; terminal states irreversible | Bugs, dashboards, agent flows |
| HIGH | Module tree — CRUD + cascade soft-delete | Deleting a module cascades to US, AC, ATC, Tests; wrong cascade = invisible data loss | Everything under a Project |
| HIGH | ATC edit propagation | "One-edit-many-tests" promise; silent breakage defeats the product's pedagogical claim | All Tests that chain the edited ATC |
| HIGH | Bug lifecycle + Jira async sync | Defect heatmap depends on `module_id`; Jira sync is best-effort but must not corrupt state | `module_defect_stats`, Jira integration |
| MEDIUM | Workspace invite flow (24h token) | User onboarding; expired tokens lock out new team members silently | `workspace_members`, RBAC |
| MEDIUM | Jira import — one-way pull + idempotency | Async worker; duplicate US/AC rows if dedup fails | `user_stories`, `acceptance_criteria`, `external_id` |
| MEDIUM | Tree-view rollup query | Read-heavy; wrong counts make the left-nav misleading without throwing errors | `modules`, `user_stories`, `atcs` counts |
| LOW | PostHog / Sentry sinks | No user-visible impact on failure | None |

## 2. What to Test First and Why

### 2.1 Auth — OAuth (GitHub / Google) + Magic-Link Email (CRITICAL)

**Why it matters**: Every flow in Bunkai is gated by authentication. A broken OAuth callback leaves all users locked out. A broken state-token validation opens the system to CSRF attacks. A bug in the "first verified login" workspace-bootstrap creates ghost users with no workspace.

**What commonly breaks**:
- OAuth state token not validated server-side → `403` not returned on mismatch (security gap)
- Callback route (`/auth/callback`) handling errors from the provider gracefully vs. crashing with a raw 500
- `EMAIL_EXISTS` scenario: user tries GitHub OAuth after registering with Google using the same email → should reject with `EMAIL_EXISTS`, not silently link or create a duplicate
- First-login workspace creation: race condition if the user double-submits or the provider callback fires twice
- Magic-link: token expiry (24h) vs. Supabase's default — if the expiry is misconfigured, tokens never expire or expire too fast

**Dependencies**: Supabase Auth, `auth.users`, `workspace_members`, JWT HttpOnly cookie, `middleware.ts`

**What an experienced QA would check**:
- Happy path: OAuth GitHub → consent → callback → workspace created → `/home`
- Error path: provider returns error → redirect to `/login` with error code AND magic-link fallback CTA visible
- State-token tampering: manually alter the `state` param in callback URL → verify `403`
- Concurrent first-logins with the same email across two providers → `EMAIL_EXISTS` behavior
- Session persistence: refresh a page after login → still authenticated (cookie + refresh token working)

---

### 2.2 Bearer PAT — Issuance + Scope Enforcement (CRITICAL)

**Why it matters**: This is the exclusive auth mechanism for AI agents and CI pipelines. If `write`-scoped tokens can be minted by `viewer` users, or if a `read`-only token can mutate state, the security model collapses for headless consumers.

**What commonly breaks**:
- Scope enforcement: `read`-only token can POST to `/runs` or `/atcs` → should `403`
- Token issuance: plain token returned ONCE and not stored → if the response is lost, the user must revoke and re-issue; a retry should NOT return the same plain token
- SHA-256 hash stored, not the plain token → verify the plain token is never logged or persisted in any response beyond the initial issuance
- `workspace_id` constraint: a token scoped to workspace A should not work against workspace B's resources
- `last_used_at` semantics: every authenticated request should bump this (token rotation UX)

**Dependencies**: `access_tokens` table, `middleware.ts`, every write endpoint

**What an experienced QA would check**:
- `read`-only token → `GET /atcs` → `200`; `POST /atcs` → `403`
- `write`-scoped token from a `viewer` user → verify role + scope intersection denies writes
- Token revocation: `DELETE /auth/tokens/{id}` → subsequent Bearer request → `401`
- Expired token (manipulate `expires_at` in test env) → `401` with clear error
- Idempotency-Key replay with a revoked token → `401`, not the cached response

### 2.3 RLS Multi-Tenancy — Workspace Isolation (CRITICAL)

**Why it matters**: Postgres RLS is the last line of defense between tenant data. If a user from workspace A can read workspace B's ATCs, the breach is silent — no error thrown, just data returned. This is the hardest class of bug to detect in manual testing because it requires a multi-tenant setup.

**What commonly breaks**:
- Missing `workspace_id` index on a new table → RLS policy runs but performs a seq scan, causing latency spikes that mask the isolation test
- Service-role bypass (`SET LOCAL row_security = off`) leaking into user-context code paths — gives blanket cross-tenant read
- RLS policy written for INSERT but missing for SELECT (or vice versa) — common after schema migrations
- `modules.path` materialized column: if path is computed without workspace scoping, a subtree query could accidentally include nodes from another workspace

**Dependencies**: Every entity carrying `workspace_id`, Supabase Auth, `workspace_members`

**What an experienced QA would check**:
- Two users in different workspaces: user A queries `/api/v1/atcs` → gets only workspace A's ATCs, zero from workspace B
- Direct Supabase table query using workspace A's JWT → workspace B rows return 0 results
- Admin API with service-role key → confirm it bypasses RLS only when called with explicit pre-filter, not as a blanket pass
- After adding a new entity to the schema, verify it has a functioning RLS policy before merging the migration

### 2.4 ATC Create (Transactional) (CRITICAL)

**Why it matters**: The ATC create transaction inserts 4 tables atomically (`atcs`, `atc_steps`, `atc_assertions`, `atc_acceptance_criteria`). A partial commit leaves orphan rows. The constraint that `user_story_id` AND at least one `acceptance_criterion_id` must be provided is the entire structural traceability guarantee — if it can be bypassed, the product's core pedagogical value is gone.

**What commonly breaks**:
- Partial transaction rollback: one of the 4 inserts fails (e.g., duplicate `atc_acceptance_criteria` row) → the `atcs` parent row is orphaned without the constraint rows
- Orphan ATC: `user_story_id` null or `acceptance_criteria` empty → server-side constraint not enforced, UI save button disabled but API not guarded
- `atc_steps` position ordering: two steps submitted with the same position → deterministic sort broken
- Realtime broadcast: after successful create, subscribed tabs must refresh the tree node without a manual reload

**Dependencies**: `atcs`, `atc_steps`, `atc_assertions`, `atc_acceptance_criteria`, `activity_log`, Supabase Realtime

**What an experienced QA would check**:
- Happy path: create ATC with 3 steps + 2 assertions + 2 AC links → verify all 4 tables have rows, `activity_log` has one entry, Realtime broadcasts
- Orphan guard: POST to `/atcs` with empty `ac_ids[]` → `400` with clear error
- Transaction rollback: mock a DB failure on `atc_assertions` insert → verify no orphan `atcs` row exists
- Idempotency: POST with same `Idempotency-Key` twice → second response returns first result, no duplicate rows

### 2.5 Run Lifecycle — Start → Step Result → Finish / Abort (HIGH)

**Why it matters**: `runs.status` has terminal states that are **irreversible**. Once `passed|failed|aborted`, the Run is frozen — no step updates accepted. The derived `run_atcs.status` must always reflect the correct fold of child statuses. If a `failed` run_atc doesn't propagate up, dashboards lie.

**What commonly breaks**:
- Terminal-state guard: `POST .../steps/{id}/result` on an already-`failed` Run → must `409`, not silently succeed
- `run_atcs.status` recomputation: a subsequent `pass` after an earlier `fail` on the same run_atc → must NOT flip back to `pass`
- `runs.progress_pct` drift: if recomputation uses integer division, a 3-step ATC with 1 complete step returns 33% but repeated calls may drift
- Abandoned agent run: sweeper cron not running → Run stuck in `running` forever; dashboards show ghost "in progress" runs
- Idempotency key collision: two agents start the same Test with the same key within 24h → second call must return the existing `run_id`, not create a duplicate

**Dependencies**: `runs`, `run_atcs`, `run_steps`, `activity_log`, Realtime, idempotency-cleanup cron, run-timeout-sweeper cron

**What an experienced QA would check**:
- Full happy path: start run → mark all steps pass → `/finish` → verify `runs.status=passed`, `run_atcs` all `pass`, `finished_at` set
- Abort mid-run: mark 2/5 steps → abort → remaining run_steps are `skipped`, `runs.status=aborted`, `abort_reason` set
- Fail + subsequent pass: mark step 1 fail → mark step 2 pass → verify `run_atcs.status` stays `fail`
- POST on terminal run → `409`
- Agent timeout simulation: create a run, don't finish it, wait for sweeper → verify auto-abort with reason "executor timeout"

### 2.6 Module Tree — CRUD + Cascade Soft-Delete (HIGH)

**Why it matters**: Soft-deleting a Module cascades to all descendants: US, AC, ATC, Tests. A missing cascade leg means orphaned entities that pass RLS but are invisible in the UI — silent data corruption. The materialized `path` column must stay consistent after every move/rename.

**What commonly breaks**:
- Cascade missing a table: `atc_acceptance_criteria` or `test_steps` not archived when ATC is cascade-archived
- Module move: cycle detection — moving Module A under one of its own descendants must fail
- Path rebuild after move: `modules.path` stale after parent change → breadcrumbs and subtree filters return wrong results
- Depth guard: creating a 7th nesting level (soft warning at 4, hard cap at 6) → must reject with clear error

**Dependencies**: `modules`, `user_stories`, `acceptance_criteria`, `atcs`, `tests`, `modules.path` materialized column

**What an experienced QA would check**:
- Soft-delete a parent module with 2 children and 3 grandchildren → verify all 5 descendant modules + their US/AC/ATC are archived
- Move module A under module B (valid) → verify `path` updated for A and all its descendants
- Attempt cycle: move module A under its own child → `400`
- Create 6 levels deep → `200`; create 7th level → `400` or `200` with warning per spec

### 2.7 ATC Edit Propagation (HIGH)

**Why it matters**: Editing an ATC mutates the steps that every chained Test executes. If propagation silently fails, agents and humans run a stale version of the test script. This is the "one-edit-many-tests" promise — breaking it defeats the product's core value prop.

**What commonly breaks**:
- `affected_test_ids` not computed or returned: caller has no confirmation that downstream Tests were affected
- Version bump logic: `atcs.version` not incremented on edit → consumers can't detect staleness
- Cascade replace: Test chains ATC v1; ATC is edited to v2; Run started after edit must execute v2 steps — if `test_steps.atc_id` is a live FK and not a snapshot, the propagation is automatic but must be verified
- Concurrent edits: two agents PATCH the same ATC simultaneously → last-write-wins without a conflict signal

**Dependencies**: `atcs`, `atc_steps`, `test_steps`, `runs` (subsequent runs post-edit)

**What an experienced QA would check**:
- Edit an ATC's step title → start a new Run on a Test that chains it → confirm the new step title appears in `run_steps`
- Edit an ATC used by 3 Tests → verify `affected_test_ids` in response includes all 3
- Historical Run preservation: a Run started before the ATC edit must still show the old step content in `run_steps` (snapshot semantics)
- Concurrent PATCH with `If-Match` (if ETags are implemented) or verify last-write-wins is explicit in the spec

## 3. State Machines That Matter

### 3.1 `runs.status` — Operational + Irreversible

The most important state machine in the system. Every incorrect terminal transition is unrecoverable without a direct DB fix.

- **Why transitions matter**: `running → aborted` via the sweeper is the only self-healing mechanism. If the sweeper is broken, the system accumulates ghost `running` Runs that block heatmaps and confuse dashboards.
- **Transitions most likely to be broken**: `running → passed` triggered by all `run_atcs=pass` happening before an explicit `POST /finish` call — the auto-close shortcut path is easy to miss in testing.
- **Terminal state guard**: any write to a terminal Run must return `409`, not `200` with a no-op.
- **Invisible corruption**: a Run stuck in `running` looks like "in progress" in the dashboard indefinitely — no alert fires unless the sweeper is monitored.

### 3.2 `bugs.status` — Operational

The reopen path (`closed → open`) is the most undertested transition in systems like this. SRS doesn't enumerate every sub-transition; the heatmap counts reopens as a quality signal — if reopen doesn't increment the counter, the metric is wrong.

### 3.3 `workspace_invites.status` — Security

24h token expiry is enforced by the signed token, not by a DB lifecycle. You'll want to verify: (a) an expired token returns a clear `410 Gone` or `401`, not a silent redirect; (b) a revoked invite's token is rejected even within the 24h window.

### 3.4 `access_tokens.status` — Security

The implicit status (derived from `expires_at` + `revoked_at`) means there's no single DB column to check — it's computed in `middleware.ts` on every request. Test revocation immediately after DELETE: the middleware must reflect the revocation on the very next request, not on a cached result.

## 4. Silent Killers — Automated Processes

These are the most undertested areas of Bunkai. All of them fail without any UI feedback to users.

### 4.1 `run-timeout-sweeper` (Every 15 min)

**What breaks if it misses**: Runs stuck in `running` forever. Agent-driven runs that crash mid-execution never close. Dashboards accumulate ghost "in progress" counts. No one notices until a QA lead manually audits the Runs table.

**How failure is detected today**: Not specified in SRS. Vercel cron logs only — no alerting defined.

**Recommended QA strategy**: Create a Run, do NOT call `/finish`, wait for sweeper tick (or simulate by setting `started_at` in the past in test env), verify Run becomes `aborted` with reason `"executor timeout"`.

### 4.2 `jira-bug-sync-retry` (Every 5 min)

**What breaks if it misses**: Bugs filed in Bunkai that should appear in Jira never sync. `jira_sync_status=failed` rows accumulate. After a long Jira outage, the retry queue may grow unbounded. The backoff logic must be tested — if it retries every 5 min with no cap, it can flood Jira when the service comes back.

**How failure is detected today**: `bugs.jira_sync_status` field — only visible if you query the table or build a UI indicator (not in MVP scope per feature-map).

**Recommended QA strategy**: Mock Jira unavailable → file a Bug → verify `jira_sync_status=failed`, no exception thrown; restore Jira → wait for retry cron → verify `jira_sync_status=synced`.

### 4.3 `module_defect_stats` materialized view refresh

**What breaks if it misses**: Defect heatmap shows stale counts. A module that just had 5 new bugs filed shows the previous count. The nightly fallback refresh means the lag can be up to 24h.

**How failure is detected today**: Only by comparing dashboard counts vs. `SELECT count(*) FROM bugs WHERE module_id = ?`.

**Recommended QA strategy**: File 3 bugs on a module → query the heatmap endpoint immediately → counts must be current (trigger-driven, not nightly). Force the nightly path by disabling triggers in test env → verify nightly fallback corrects the count.

### 4.4 `tsvector` GIN index update (On ATCs INSERT/UPDATE)

**What breaks if it misses**: ATC search and autocomplete returns stale or missing results. A newly created ATC with a distinctive title won't appear in search. Silent degradation — users assume no ATC exists and create a duplicate.

**How failure is detected today**: Not detectable without searching for a known-just-created ATC.

**Recommended QA strategy**: Create an ATC with a unique title → immediately search for that title → verify it appears in results with correct `ts_rank`.

### 4.5 Jira import worker (async, Vercel cron-triggered)

**What breaks if it misses**: User Stories + ACs don't appear in Bunkai after a Jira JQL import. Import row may be stuck `pending` or `running` forever. Since imports are one-way and idempotent, a missed import is recoverable by re-triggering — but only if the user knows to retry.

**How failure is detected today**: `GET /imports/{id}` polling endpoint returns `status` — but only if the user actively polls it. No push notification in MVP.

**Recommended QA strategy**: Queue a Jira import → simulate worker crash mid-pagination → verify import row is `failed`, not `running`; verify re-triggering the import dedupes via `external_id` and does not create duplicate US rows.

## 5. External Integrations — Failure Points

### 5.1 Supabase Auth

- **Which flow stops if down**: ALL UI flows. No login = no access.
- **Critical timeouts**: JWT is 1h access + 30d refresh. If the refresh endpoint is down, users get logged out after 1h.
- **Acceptable degradation**: None — Auth is the hard dependency. If Supabase Auth is unreachable, the system is fully down for browser users (Bearer PAT flows continue if middleware can validate token hash from Postgres directly).
- **Known quirk**: OAuth state token validation must happen server-side. If `middleware.ts` skips this check for performance, it opens a CSRF vector.

### 5.2 Jira (Atlassian)

- **Which flow stops if down**: Jira import (Flow 1 Step 5) and Bug sync (Flow 2 Step 5). Core flows (ATC authoring, run execution) are unaffected.
- **Acceptable degradation**: Bug sync → `jira_sync_status=failed`, retry cron picks up later. Import → user is notified via polling endpoint. Both are best-effort by design.
- **Known quirk**: Jira REST rate limits. Import pagination that fires many requests per minute may get rate-limited mid-job. Worker must handle `429` with exponential backoff and resume from the last successful page.

### 5.3 Cloudflare R2 / MinIO

- **Which flow stops if down**: Evidence upload in Run execution (Flow 2 + Flow 3). Step can still be marked pass/fail with empty evidence — degraded but functional.
- **Acceptable degradation**: Step records result with null `evidence_url`. UI shows a placeholder instead of broken image. Run can still be completed.
- **Known quirk**: Signed URL expiry. If the upload takes longer than the signed URL TTL (typically 15–60 min), the upload fails silently. Large evidence files (video traces) are most at risk.

### 5.4 Vercel Cron (or BullMQ in Community edition)

- **Which flow stops if down**: All cron jobs (run-timeout sweeper, idempotency-cleanup, defect-stats fallback, jira-bug-sync-retry). See §4 Silent Killers.
- **Acceptable degradation**: System continues to function for active users. Degradation is invisible and cumulative — tables grow, Runs get stuck, heatmaps go stale.

## 6. Dependency Cascade Between Flows

```
Supabase Auth
  └─► JWT / PAT verified by middleware.ts
        └─► RLS workspace isolation
              ├─► Flow 1: Setup (Workspace → Project → Module → US → AC → ATC)
              │     └─► ATC transactional create (4-table insert)
              │           └─► Tests (chain ATCs)
              │                 └─► Flow 2 / Flow 3: Run execution
              │                       ├─► run_atcs status derived
              │                       ├─► runs.progress_pct
              │                       ├─► Bug filing → module_defect_stats ──► Heatmap
              │                       │     └─► Jira sync async worker
              │                       └─► Realtime fan-out → live dashboard
              └─► Bearer PAT (headless)
                    └─► Flow 3: Agent-driven Run (same endpoints as Flow 2)
                          └─► Idempotency keys → safe retry
```

**Most critical chain**: Auth → RLS → ATC create → Run execution. If any link breaks, everything downstream of it fails. Testing flow 2 in isolation without a real RLS-validated workspace context hides the most dangerous class of bugs.

**Second critical chain**: Bug filed → `module_defect_stats` refresh → heatmap. If the materialized view trigger is missing from a new environment (e.g., after a DB reset), the heatmap is permanently stale and no error is thrown.

## 7. Edge Cases Developers Commonly Forget

### Concurrency
- Two users create an ATC with the same slug simultaneously in the same module → unique constraint violation must be surfaced as a `409`, not a `500`
- Two agents start the same Test with the same idempotency key in the same 24h window → second call must return the first `run_id` (idempotent), not create a duplicate
- Concurrent `run_step` results posted for the same step from two processes → last-write-wins or `409` — needs to be deterministic

### Data Limits
- `modules` tree depth: creating level 7 (cap is 6) → must be blocked server-side, not just in the UI
- `atc_steps` position ordering: 100+ steps in one ATC → rebalance logic must not produce non-unique positions
- `bugs.evidence_urls[]` is an array — what is the max items? What happens when a very large evidence URL is stored (Cloudflare R2 URLs can be long with signed params)?

### Orphaned States
- An ATC with `user_story_id` pointing to an archived (soft-deleted) US — should the ATC itself be archived? Or can it remain active on a ghost US? The cascade spec says yes, but it should be verified.
- A Run whose Test is soft-deleted mid-execution — the Run must still complete or abort cleanly; the UI must not crash when navigating to a Run whose Test no longer appears in the Module tree.

### Idempotency
- POST `/runs` twice with the same `Idempotency-Key` after the 24h window expires → second call should create a new Run (key expired), not return the old one
- POST `/bugs` with the same `Idempotency-Key` → second call must return first Bug; a bug with a reverted `status` on the first call must not create a duplicate

### Permission Boundaries
- A `viewer` user calling `POST /atcs` → `403`, not a `401` (authenticated, just unauthorized)
- A `member` user trying to delete a Project (owner-only) → `403` with clear error
- A `write`-scoped token with `workspace_id` constraint calling an endpoint in a different workspace → `403`

### Timezone / DST
- `workspace_invites` token expiry: 24h from creation in UTC. If the server generates the token in local time and the verification is UTC (or vice versa), invites expire at unexpected times for users in non-UTC timezones.
- Run `started_at` / `finished_at`: both must be UTC ISO-8601. Dashboards aggregating by day must handle DST transitions in user-local timezone.

## 8. Pre-Release Checklist (Priority-Ordered)

1. Verify OAuth callback validates state token server-side → `403` on mismatch
2. Verify RLS: user from workspace A cannot read any row owned by workspace B (cover all entity types)
3. Verify `POST /atcs` without `ac_ids[]` returns `400` (orphan guard)
4. Verify Run terminal-state guard: `POST .../result` on a `failed` Run returns `409`
5. Verify `run_atcs.status` after a fail: subsequent `pass` does NOT flip status back
6. Verify cascade soft-delete: archive parent module → all descendant US/AC/ATC/Tests are archived
7. Verify module-move cycle detection: move A under its own child returns `400`
8. Verify Bearer PAT `read`-only token cannot POST to any write endpoint (`403`)
9. Verify ATC edit propagation: new Run on a Test that chains the edited ATC executes the new step content
10. Verify `jira-bug-sync-retry` cron: bug with `jira_sync_status=failed` is retried and eventually synced
11. Verify `run-timeout-sweeper`: a run abandoned for > `max_duration` becomes `aborted` with reason
12. Verify ATC FTS index: newly created ATC appears in search immediately (GIN index updated)
13. Verify invite token expiry: `410` or `401` returned after 24h (not silent redirect to homepage)
14. Verify Jira import idempotency: re-triggering same JQL does not duplicate `user_stories` rows
15. Verify Realtime broadcast: ATC create in one browser tab triggers tree node refresh in a second tab
