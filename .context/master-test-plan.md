## 1. Executive Risk Map

Bunkai stopped being an authoring-only tool this cycle and became a closed-loop TMS: ATCs chain into Tests, Tests execute as Runs with per-step evidence, failed steps raise Bugs, and the whole User Story → ATC → Test → Run → Bug chain is now queryable in one Traceability report. That's a much larger blast radius than June's plan covered — 8 new tables, 6 new automated triggers, and an entire execution domain that simply didn't exist before. **Identity + multi-tenancy remains the hard prerequisite** underneath all of it: if auth or RLS breaks, every one of those new surfaces becomes unsafe or inaccessible. Both security bugs open in June (member-role PAT self-escalation, Bearer ignoring workspace switch) are now fixed in code — but one has a real residual risk worth chasing (§11 GAP-14: ~136 pre-fix admin-scoped PATs were never confirmed revoked). The single biggest correction this round: June's plan treated ATC creation as an unsafe app-layer transaction after a claimed RPC removal — that claim was **flatly wrong**. The RPC was never removed; ATC creation has always been (and remains) a single atomic DB-layer transaction. Drop any test suite built around "simulate a crash and check for orphan `atc_steps`" — that risk was never real.

## 2. What to Test First and Why

### 2.1 RLS Multi-Tenancy — Workspace Isolation (CRITICAL)

**Why it matters**: Postgres RLS is the last line of defense between tenants. If a user in workspace A reads workspace B's data, the breach is silent — no error, just rows that shouldn't be there. This is the hardest bug class to catch because it needs a genuine multi-tenant test setup, and it's the one area this round's data-map regen explicitly flagged as "not re-queried" — the policy pattern is carried forward from June on trust, not re-verified.

**What commonly breaks:**
- 8 new tables since June (`runs`, `run_atcs`, `run_steps`, `bugs`, `notifications`, `notification_preferences`, `milestones`, `project_environments`) — each needs its own RLS policy; a migration that adds the table but forgets the policy is a live cross-tenant leak
- RLS policy written for INSERT but missing for SELECT (common after fast-moving migrations — this repo shipped 8 tables in one cycle)
- Service-role bypass leaking into a user-context code path
- Traceability report's RPC (`bunkai_report_story_traceability`) joins 5 tables in one call — a single missed `workspace_id` filter anywhere in that join leaks data from every joined table at once

**Dependencies**: Every entity with `workspace_id`, Supabase Auth, `workspace_members` (RLS anchor)

**What an experienced QA would check:**
- Two users in different workspaces: user A queries every one of the 8 new endpoints → zero rows from workspace B, especially `runs`, `bugs`, `notifications`
- Traceability report for a workspace-B story, requested by a workspace-A member → `404`, not a partial/leaked chain
- After any schema migration adding a new entity, verify a SELECT-scoped RLS policy exists before treating the feature as done
- Archive cascade in workspace A must not touch entities in workspace B

### 2.2 Auth — Magic-Link + Headless + BK-166 OTP Confirm (CRITICAL)

**Why it matters**: Every flow is gated by authentication, and the number of issuance paths grew since June — password sign-in now sits alongside a mandatory 6-digit OTP confirmation step for new sign-ups (BK-166), with no bypass. More paths means more places for a session or PAT to be minted incorrectly.

**What commonly breaks:**
- BK-166 OTP: the 6-digit code must genuinely block account usability until confirmed — no `email_confirm: true` shortcut exists anymore (that was June's model; this is a materially different flow)
- `POST /auth/resend` must invalidate the prior code, not just send a new one that both remain valid
- Magic-link: `consumed_at` single-use is still enforced app-layer, not atomically — a race between two concurrent requests with the same token is still a real risk (unchanged from June)
- Cross-device magic-link: a fix was attempted (BK-400) then **explicitly reverted** as "the dangerous part" — do not test this expecting it to work; the send side is still PKCE/same-device only
- Every headless mint point (signin, confirm) uses `DEFAULT_PAT_SCOPES`, which excludes `workspace:admin` by design — verify this holds on every new mint path, since a regression here silently reopens BK-134/135-shaped risk through a different door

**Dependencies**: Supabase Auth, `magic_link_tokens`, `workspace_members`, JWT/session cookie, `lib/api/principal.ts`

**What an experienced QA would check:**
- Sign-up → OTP required before any workspace access → resend invalidates the old code
- Magic-link replay: consume once → replay same URL → rejected, not re-authenticated
- Cross-device magic-link click → confirm it still fails (regression guard against an accidental re-introduction of BK-400)
- Every headless-minted PAT → confirm scopes exclude `workspace:admin`
- OAuth callback with a tampered `next` param → rejected server-side (carried gap, not re-verified this round — see §11)

### 2.3 Bearer PAT — Issuance + Scope Enforcement (CRITICAL, residual risk open)

**Why it matters**: This is the exclusive auth mechanism for AI agents and CI. BK-134/135 (member-role users self-issuing `workspace:admin` PATs) is **fixed in code** — `assertTokenIssuanceAuthorized()` now gates the scope by role before minting. But the fix only stops *new* self-issuance. The ~136 admin-scoped PATs minted on staging *before* the fix landed were never confirmed revoked (GAP-14). If any of those are still active, the vulnerability is still live in practice even though the code is fixed.

**What commonly breaks:**
- **GAP-14 (open)**: pre-fix `workspace:admin` PATs still un-revoked — query `access_tokens` for admin-scoped tokens minted before the fix date and confirm they're either revoked or were legitimately owner/admin-issued
- Regression on the fix itself: member-role user attempts `workspace:admin` issuance → must `403`, not `201`
- `assertWorkspaceContext()` re-checks the workspace binding on every call, not just at mint — an admin PAT must never act outside its issuing workspace, even for a workspace the underlying user also administers elsewhere
- `assertNoGlobalAdminScope()`: no headless path should ever be able to mint a `workspace_id=NULL` global admin token
- PATs cannot mint PATs — a Bearer-authenticated `POST /api/v1/tokens` must `403`

**Scopes (confirmed, unchanged since June):** `atc:read`, `atc:write`, `run:execute`, `workspace:admin`

**Dependencies**: `access_tokens`, `lib/api/pat.ts`, `lib/api/principal.ts`, every write endpoint

**What an experienced QA would check:**
- Query staging for pre-fix admin-scoped PATs still active — this is a data audit, not just a code test, and it's the single highest-value check in this plan right now
- Member user attempts `workspace:admin` PAT mint → `403` (BK-134/135 regression gate)
- Admin PAT used against a workspace the user administers elsewhere → `403` (workspace-binding still holds)
- Revocation: `DELETE /api/v1/tokens/{id}` → immediate `401` on next Bearer request, no caching window
- Bearer-authenticated `POST /api/v1/tokens` → `403` (PAT-from-PAT still blocked)

### 2.4 Manual Run Execution — Start / Mark / Finish / Abort (CRITICAL, new domain)

**Why it matters**: This is the feature that turns Bunkai from a test-case authoring tool into an actual TMS — someone executes a Test and the result is recorded per-step, not just per-ATC. It was 100% Backlog/Planned in June; all six sub-features shipped this cycle (BK-182 epic). It's also the entry point for two other new domains: Bug filing happens from a failed run step, and Notifications fire on run completion.

**What commonly breaks:**
- `Idempotency-Key` is now a **hard-required** header on `POST /runs`, not an optional nicety — a test suite written against June's "planned, unwired" understanding will fail for the wrong reason (missing header, not a real bug) if not updated
- `resolveRunWorkspaceId()` for Bearer callers with no active-workspace cookie was deliberately left untouched by the BK-316 fix (per the commit message: fixing it there would revert the BK-182 behavior) — worth a dedicated test confirming both fixes coexist correctly, since they touch adjacent code
- `runs_abort_reason_chk` is a **DB CHECK constraint**, not just a frontend form validation — an abort with an empty/null reason must fail at the DB layer even if a crafted request bypasses the API-layer check
- On `finish`, remaining `pending` steps must auto-transition to `skipped` — a step left in `pending` after a run is marked finished is a data-integrity bug
- `run_atcs` snapshots the ATC title at run-start time — editing the source ATC afterward must NOT change the historical run's recorded title (denormalized on purpose, for history stability)

**Dependencies**: `runs`, `run_atcs`, `run_steps`, `tests`, `test_steps`, `project_environments`, `idempotency_keys`, Bug filing, Notifications

**What an experienced QA would check:**
- Start a run without `Idempotency-Key` → hard failure (confirm the header is truly required, not silently optional)
- Start the same run twice with the same `Idempotency-Key` within 24h → second call returns the first run, no duplicate
- Abort with empty `abort_reason` via a crafted request bypassing client validation → still rejected (DB CHECK, not just API check)
- Finish a run with steps still `pending` → those steps auto-`skipped`, run status set correctly
- Edit the ATC an already-finished run used → the run's `run_atcs` denormalized title stays unchanged

### 2.5 Workspace Switching — Bearer Rejection (CRITICAL, regression-only)

**Why it matters**: BK-316 fixed a bug where a Bearer/PAT caller's active-workspace switch silently no-op'd instead of failing. The fix is a hard `403` for any Bearer caller hitting this endpoint — a PAT's workspace binding is fixed at mint time and was never meant to be switchable. This is now a pure regression-guard: a `200` here is not "the feature working," it's the bug coming back.

**What commonly breaks:**
- Any future refactor of `lib/api/principal.ts` or the active-workspace cookie logic that accidentally lets a Bearer caller fall through to the cookie-path success case
- Confusing this with `resolveRunWorkspaceId()` in the Run-start flow (§2.4) — that path deliberately resolves workspace differently for Bearer callers and was *intentionally* not touched by this fix; the two must not be conflated when writing regression coverage

**Dependencies**: `access_tokens`, `workspace_members`, `bk_active_ws` cookie

**What an experienced QA would check:**
- Bearer-authenticated `POST /me/active-workspace` → `403`, always, regardless of the target workspace's validity
- Cookie-authenticated `POST /me/active-workspace` for a workspace the user belongs to → `200`, cookie set correctly (happy path still works)
- Confirm `GET /me` for a Bearer caller reflects the PAT's own workspace binding, not any stale cookie state

### 2.6 ATC Create + Edit — Unified REST, RPC-Backed (HIGH — corrected from June)

**Why it matters**: "One edit, many tests" is the core product promise. June's plan flagged this as CRITICAL on the theory that the atomicity guarantee had degraded to an app-layer transaction after an RPC removal. **That theory was wrong.** The RPC (`bunkai_create_atc` / `bunkai_update_atc`) was never removed; both creation and editing have always run as single DB-layer SECURITY DEFINER transactions. Downgraded to HIGH because the atomicity risk that justified CRITICAL never existed — but the flow is still core product value and worth thorough coverage.

**What commonly breaks:**
- Creation is now REST-only for **both** browser and machine callers — the browser's `NewAtcEditor` calls the same `POST /api/v1/atcs` a CLI would, so there's no longer a separate browser-only code path to diverge
- Editing still has two entry points (Server Action for browser, REST `PATCH` for machine) but both call the same underlying RPC — the one real remaining difference is optimistic locking: REST requires `X-If-Match` and `409`s on mismatch; the browser Server Action passes `ifMatch: null` (last-write-wins, by design, not a bug)
- Anchoring invariant: every ATC still requires ≥1 User Story + ≥1 Acceptance Criterion, validated before the RPC runs
- `affected_test_count` in the edit response is now meaningful (Test Builder is live) — verify it actually reflects how many Tests chain the edited ATC, not a stale `0`

**Dependencies**: `atcs`, `atc_steps`, `atc_assertions`, `atc_acceptance_criteria`, `tests` (for `affected_test_count`), Supabase Realtime

**What an experienced QA would check:**
- Create via browser and via a raw REST call with the same payload → identical resulting rows, same RPC path
- Edit an ATC chained by 2 Tests → `affected_test_count: 2` in the response
- REST `PATCH` with a stale `X-If-Match` → `409`; browser Server Action edit of the same ATC concurrently → last-write-wins, no error
- Omit `steps` from a `PATCH` body → steps cleared (full-replace semantics), not left in place

### 2.7 Bug Filing + Consistency Trigger (HIGH, new domain)

**Why it matters**: Bugs are raised from a failed run step, and a DB trigger (`bugs_check_consistency`) validates that the run/step/ATC/project all genuinely belong together before the insert is allowed. This is a data-integrity guard enforced at the database layer, not just app-layer validation — worth deliberately trying to defeat.

**What commonly breaks:**
- A crafted payload referencing a `run_step` from Run X but an `atc`/`project` that doesn't actually belong to that run → should be rejected by the trigger, not just by app-layer checks that a direct-to-DB or malformed request could bypass
- Status transitions are forward-only (BK-264) — attempting to move a bug backward in its status lifecycle must be rejected
- Assign/reassign/unassign each fire `activity_log_notify_bug_event`, which writes a `notifications` row — a silent trigger failure means the assignee never finds out, with no visible error anywhere
- **New (BK-337/BK-466)**: evidence URLs on bug filing must reject `javascript:`/`data:` schemes — the same `z.url({protocol: z.regexes.httpProtocol})` http/https-only guard previously confirmed only on run-step evidence (`lib/runs/validation.ts`) is now mirrored in `lib/bugs/validation.ts`. A regression on either side reopens a stored-link injection path the other side already closed.
- **New (BK-337)**: `GET /api/v1/bugs/{id}` now returns origin provenance (which Run/run_step raised the bug) and an archived-module tag — a bug whose module is later archived must stay auditable, not silently lose its trail

**Dependencies**: `bugs`, `run_steps`, `atcs`, `activity_log`, `notifications`

**What an experienced QA would check:**
- File a bug with a mismatched run_step/atc/project combination → rejected by the DB trigger
- Attempt a backward status transition → rejected
- Assign a bug → verify a `notifications` row is actually created for the assignee, not just that the assignment succeeded
- Bug heatmap and recovery-cycle metrics reflect newly filed/resolved bugs without a manual refresh needed
- File a bug (and, separately, mark a run step) with an evidence URL using a `javascript:`/`data:` scheme → rejected on **both** paths, not just one
- `GET /api/v1/bugs/{id}` for a bug whose module was archived after filing → provenance link to the originating run/step still resolves

### 2.8 Traceability Chain Report — Anti-Enumeration (HIGH, new domain)

**Why it matters**: This report answers "is this User Story actually covered, and did the covering tests pass?" by joining User Story → ATC → Test → Run → Bug in one read. It's deliberately non-disclosing on error: a missing, foreign-workspace, or wrong-project story ID all collapse to the same `404` — never a `403` — specifically to avoid leaking cross-workspace story existence. Getting this status code wrong in either direction is a real bug: a `403` instead of `404` confirms the story exists in another workspace (information disclosure); a `200` with partial data is a straightforward RLS leak.

**What commonly breaks:**
- Any of the three failure shapes (missing / foreign-workspace / wrong-project) returning a different status code than the other two — they must all be indistinguishable from the outside
- The export feature is 100% client-side HTML generation from already-fetched data — verify it doesn't accidentally trigger a second, unfiltered fetch that bypasses the RLS-scoped chain already rendered on screen
- Filter combinations (result, module, date range) — a filter that silently returns zero rows instead of erroring on an invalid module ID belonging to a different project

**Dependencies**: `user_stories`, `atcs`, `tests`, `runs`, `bugs` (read-only join, no dedicated table)

**What an experienced QA would check:**
- Missing story ID, a story ID from another workspace, and a valid story ID from the wrong project → all three return the identical `404` shape
- Happy path: a story with ATCs, Tests, Runs, and a Bug attached → the assembled chain reflects all of it accurately
- Export the chain → confirm the downloaded HTML matches exactly what was on screen, no extra data pulled

## 3. State Machines That Matter

### 3.1 `runs.status` (NEW)

```
running ──► passed
       ├──► failed
       └──► aborted   (abort_reason REQUIRED — DB CHECK constraint
                        runs_abort_reason_chk, not just app-layer)
```

- **Why it matters**: this is the terminal record of whether a Test actually passed. A wrong transition here corrupts the entire quality signal the rest of the system (Bugs, Traceability, coverage dashboards) is built on.
- **Most likely broken**: `abort_reason` enforcement — verify both the API layer and the DB CHECK constraint independently, since a bypass of one without the other is the actual risk.
- **Terminal guard**: no transition exists back to `running` from any terminal state.
- **Detection**: any run stuck in `running` indefinitely (crashed tab, network drop) has no automatic reclaim — there is no timeout sweeper (§4, §11).

### 3.2 `run_atcs.status` / `run_steps.status` (NEW)

```
pending ──► passed
       ├──► failed
       ├──► blocked
       └──► skipped   (auto-set on parent run finish/abort for any
                        step never explicitly marked)
```

- **Why it matters**: per-step results feed Bug filing and the Traceability report directly. A step silently staying `pending` after its parent run finishes corrupts both.
- **Most likely broken**: the auto-skip transition on `finish`/`abort` — verify it actually fires for every unmarked step, not just the last one touched.

### 3.3 `atcs.status` — CONFIRMED DEAD (correction from June)

June's plan treated this as a live-but-partially-documented state machine, expecting `passed`/`failed` to eventually be set by run execution. Now that runs shipped, this is directly falsifiable: **`atcs.status` is never written by any production code path** — it stays `'unrun'` forever. Real per-execution status lives on `run_atcs.status` / `run_steps.status` (§3.2). **Do not write any test asserting `atcs.status` changes on run completion — it never will, by design or by oversight, and either way it's not a bug to chase.**

### 3.4 `bugs.status` — Forward-only (BK-264)

- **Why it matters**: a bug lifecycle that can move backward undermines the recovery-cycle metrics built on top of it (time-to-resolve calculations assume monotonic progress).
- **Most likely broken**: an attempted backward transition should be rejected outright, not silently accepted and left for the metrics to misreport later.

### 3.5 `workspace_invites` — Security (unchanged since June)

7-day expiry, app-layer enforced. Rotated state resets all prior lifecycle fields atomically. Most likely broken: `rotated` path failing to clear `accepted_at`, letting a stale acceptance appear valid.

### 3.6 `import_jobs` — Operational (unchanged since June)

```
queued → running → completed
                └→ failed
```

At most one active import per project (`409` on concurrent attempt). Silent-failure risk: `status=failed` with per-issue `errors[]` is a valid partial-success state, only detectable by polling.

### 3.7 `user_stories.status` — Now RPC-gated (improved certainty since June)

`draft → ready_to_test`, now confirmed as an explicit `bunkai_ready_to_test_gate` RPC (was inferred from an event side-effect in June). Full enumeration of every valid status value is still not exhaustively confirmed (§11 NEW-G3, carried).

## 4. Silent Killers — Automated Processes

June's doc only knew about 2 DB triggers. This update found 10. Treat this whole section as substantially expanded, not just refreshed.

### 4.1 `bugs_check_consistency` (NEW — trigger on `bugs` INSERT/UPDATE)

**What it does**: Validates that the run_step/ATC/run/project referenced in a bug all genuinely belong together before allowing the write.

**What breaks if it fails**: A bug could be filed pointing at mismatched entities — a data-integrity hole that corrupts the Traceability chain and bug heatmap silently, since nothing in the UI would flag the mismatch.

**How failure is detected today**: Not detectable without directly querying for cross-entity mismatches in `bugs`.

**Recommended QA strategy**: Attempt to file a bug with a deliberately mismatched run_step/ATC/project combination via a raw API call → confirm the trigger rejects it, not just the app-layer validation.

### 4.2 `activity_log_notify_bug_event` / `activity_log_notify_run_event` (NEW — triggers on `activity_log` INSERT)

**What it does**: Writes a `notifications` row whenever specific bug or run events land in `activity_log` (bug assigned/reassigned/unassigned/status_changed; run finished/aborted). This is the entire notification system — it is DB-driven, not app-code-driven.

**What breaks if it fails**: A user never learns a bug was assigned to them or a run they care about finished — with zero visible error anywhere, since the primary action (assigning the bug, finishing the run) still succeeds.

**How failure is detected today**: Only by noticing a notification never arrived — no alerting exists.

**Recommended QA strategy**: For each triggering event, assign/reassign a bug and finish/abort a run → verify a `notifications` row exists with the correct `event_type`, `entity_type`, and payload immediately after.

### 4.3 `bunkai_atcs_refresh_tsv` (carried from June)

Recomputes the search tsvector on ATC insert/update. Failure means a newly created or renamed ATC doesn't appear in search — users assume it doesn't exist and create a duplicate, defeating the reuse model this whole product is built on.

**Recommended QA strategy**: create an ATC with a unique title token → search for it immediately → verify it appears with correct rank. Repeat after an edit.

### 4.4 `*_set_updated_at` triggers (6 tables: `atcs`, `tests`, `runs`, `bugs`, `notification_preferences`, `milestones`)

Bookkeeping — sets `updated_at` on UPDATE. Silent if broken: optimistic-locking comparisons (`X-If-Match` on ATC edit) and audit timestamps go stale with no user-visible symptom.

**Recommended QA strategy**: UPDATE each of the 6 tracked entities → verify `updated_at` changes to within 1 second of the request.

### 4.5 Cron-less system — stuck-job risk (carried + worsened since June)

**What it does**: Nothing. There is still no `vercel.json` cron config, no `pg_cron`, no timeout sweeper anywhere in the codebase — confirmed absent, not just undocumented.

**What breaks if it fails**: A `runs` row (new since June — crashed browser tab, dropped network mid-execution) or an `import_jobs` row abandoned mid-flight has **no automatic reclaim path** and shows `running`/`queued` forever. This is a documented, accepted risk in Jira (STORY-BK-17 comments) — not yet mitigated, and now applies to a second table (`runs`) that didn't exist in June.

**How failure is detected today**: Not detected at all — only visible by manually noticing a run or import stuck for an implausible duration.

**Recommended QA strategy**: Start a run, abandon it mid-flight (close the tab / kill the request) → confirm it stays `running` indefinitely with no automatic timeout. This is a known-accepted gap, not a bug to file — but worth a synthetic probe in any monitoring/alerting story, since it's currently invisible to everyone including the team.

### 4.6 Supabase Realtime — 4 channels now (was 2)

**What it does**: ATC tree refresh, import progress, run step live updates (`run_atcs`/`run_steps` — `runs` itself is deliberately excluded from publication), and notification bell/toast updates (reuses the run channel's reconnect logic).

**What breaks if it fails**: Each surface has a fallback (polling for import, manual reload for ATC tree) except notifications, which has no documented fallback — a dropped Realtime connection means the bell simply never updates until the next page load.

**Recommended QA strategy**: Create an ATC / start a run / file a bug in one tab → verify the effect (tree refresh / step update / notification) appears in a second open tab without reload. Repeat with the Realtime connection deliberately dropped to confirm the fallback (or lack of one) behaves as expected.

## 5. External Integrations — Failure Points

### 5.1 Supabase Auth

- **Which flow stops if down**: All UI flows. No login, no access.
- **Critical timeout**: JWT is 1h access + 30d refresh — refresh-endpoint unreachability logs users out after 1h.
- **Acceptable degradation**: None for UI users — hard dependency.
- **Known quirk**: BK-166 OTP confirmation is mandatory with no bypass — a code-delivery failure genuinely blocks account activation, unlike June's `email_confirm: true` shortcut which no longer exists.

### 5.2 Jira (Atlassian)

- **Which flow stops if down**: Jira import only. Core flows (authoring, execution, defects) are unaffected.
- **Acceptable degradation**: Import fails with per-issue `errors[]`; safe to retry (idempotent by `external_id`).
- **Known quirk (carried, unconfirmed)**: `integrations` config table still not in DB — how Jira credentials are actually configured in staging remains unverified. Confirm before writing import tests.

### 5.3 Resend (Email) — GAP-5, still open

- **Status**: `RESEND_API_KEY` exists in `.env.example` but is consumed only by the CLI installer, never by application code. No `resend` package installed, no client anywhere.
- **Practical impact**: Invite flow remains out-of-band URL sharing by design (documented as intentional MVP scope) — but this is worth a one-line confirmation with the product owner that it's still the accepted decision, not a forgotten gap, given how much else shipped this cycle.

### 5.4 Sentry / PostHog — corrected, not implemented

- **Status**: June's doc listed these as live observability sinks. **They are not.** No packages installed, no init code anywhere — they exist only as aspirational text in architecture docs.
- **Practical impact**: Do not expect any error-tracking visibility during a test session. If a bug needs a stack trace, it has to come from application logs or manual reproduction — there is no APM safety net.

### 5.5 Cloudflare R2 / MinIO — still not started

- **Status**: Zero code wiring, confirmed more definitively this round than June's "not testable yet" — no SDK, no env var usage beyond architecture-doc mentions.
- **Acceptable degradation (when eventually live)**: Not applicable yet — this remains fully out of scope until it ships.

## 6. Dependency Cascade Between Flows

```
Supabase Auth
  └─► Session / Bearer PAT resolved by lib/api/principal.ts
        └─► RLS workspace isolation
              ├─► Workspace + Invite flows
              │     └─► Project → Module (cascade archive)
              │           └─► User Story → Acceptance Criteria
              │                 └─► ATC create/edit (RPC-backed, atomic)
              │                       └─► Test (chain ATCs, full CRUD)
              │                             └─► Run (execute a Test) 🆕
              │                                   ├─► Bug (from failed step) 🆕
              │                                   │     └─► Notification (trigger-driven) 🆕
              │                                   └─► Traceability report (reads the whole chain) 🆕
              │
              └─► Bearer PAT ────────────────────────┐
                    └─► Scope + workspace-context enforcement
                          └─► All write ops ◄─────────┘
                                └─► Idempotency keys (24h TTL)
                                      └─► Required on Run start (was optional/planned in June)
```

**Most critical chain**: Auth → RLS → ATC → Test → Run → Bug → Notification/Traceability. Every one of the last three links (Run, Bug, Notification) is new this cycle — testing ATC authoring in isolation, the way June's plan emphasized, now hides breakage that only surfaces once a Run actually executes and a Bug gets filed from it.

**Residual risk chain (open)**: Pre-fix `workspace:admin` PATs (minted before BK-134/135 landed) → if any remain un-revoked → bypass every role check the fix now enforces for new tokens. This chain is a data-audit question, not a code-test question — see §11 GAP-14.

**New silent chain**: A Run abandoned mid-flight (crashed tab) → stays `running` forever (no sweeper) → never produces a Bug, never fires a `run.finished` notification → the Traceability report for that Test permanently shows an incomplete chain with no error anywhere explaining why.

## 7. Edge Cases Developers Commonly Forget

### Concurrency
- Two Run-start requests with the same `Idempotency-Key` within 24h → second must return the first run, not create a duplicate — now load-bearing behavior since the header is required, not optional
- `magic_link_tokens.consumed_at` race: two concurrent requests with the same token — app-layer check is not atomic (unchanged risk since June)
- Two agents mark the same run step simultaneously with different results → last-write-wins behavior should be deliberate, not accidental

### Data Limits
- `modules` tree depth cap at 6 (unchanged) — verify still enforced server-side after this cycle's other changes
- `run_atcs`/`run_steps` for a Test with a very long ATC chain — verify step-ordering and marking remain correct at scale, this is untested territory since the domain is brand new

### Orphaned States (Live Risk, expanded since June)
- A Run left `running` forever with no sweeper (§4.5) — the closest thing to an orphaned state this system currently has, and it's now more consequential since Runs feed Bugs and Notifications downstream
- An ATC archived after being referenced by a `run_atcs` snapshot — the snapshot's denormalized title must remain stable; verify the archived ATC doesn't disappear from historical run views

### Idempotency
- `POST /runs` without `Idempotency-Key` → hard failure, confirm this is actually enforced and not silently accepted (§2.4)
- `Idempotency-Key` reuse after the 24h TTL expires → new resource created, not a replayed stale result
- Import job idempotency (dedup by `external_id`) — unchanged since June, still worth a regression check given how much else in the codebase moved

### Permission Boundaries
- `viewer` role calling any write endpoint across the 5 new domains (Runs, Bugs, Notifications, Milestones, Environments) → `403`, not `401` — each new domain needs its own permission-boundary sweep, not an assumption that it inherits the old domains' behavior correctly
- Admin-scoped PAT calling an admin-gated endpoint in a workspace it isn't bound to → `403` (`assertWorkspaceContext`)
- Pre-fix admin PATs (§2.3, §11 GAP-14) — treat as a live permission-boundary risk, not a closed one

### Timezone / DST
- `workspace_invites.expires_at`: 7 days from creation in UTC — unchanged risk since June
- `runs.started_at`/`finished_at` and `bugs` timestamps — new surfaces, worth confirming they're UTC ISO-8601 consistently now that recovery-cycle metrics (time-to-resolve) depend on accurate duration math
