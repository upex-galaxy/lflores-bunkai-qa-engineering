## 1. Executive Risk Map

Bunkai's fragility is concentrated in three layers. **Identity + multi-tenancy** is the hard prerequisite: if auth or RLS breaks, every feature becomes unsafe or inaccessible. **The ATC authoring pipeline** is the core product value — and its atomicity guarantee changed architecturally: the `bunkai_save_atc` SECURITY DEFINER RPC was removed; creation is now an app-layer transaction in Next.js, weaker by design. Third, there is an **active privilege-escalation bug** (BK-134/135): member-role users can self-issue `workspace:admin` PATs — 136 such tokens are already active on staging. This is not a future risk; it is the current state.

Run execution and bug tracking remain Phase 2 (`runs`, `run_atcs`, `bugs` tables not in DB). Testing those flows is blocked. The risk map below reflects only what is actually testable today.

| Priority | Flow | Why it matters | Depends on / Affects |
|---|---|---|---|
| CRITICAL | **PAT privilege escalation** (BK-134/135 OPEN) | Member users minting `workspace:admin` PATs — live security breach on staging | `POST /api/v1/tokens`, all admin-gated endpoints |
| CRITICAL | Auth — magic-link + headless (signin/signup) | Security gateway; every flow is behind auth; 4 code paths, each different failure mode | Workspace creation, RLS policies, JWT cookie |
| CRITICAL | Bearer PAT — scope enforcement | AI agents + CI use exclusively; wrong scope = privilege escalation (already exploited via BK-134/135) | All headless-mode flows |

## 2. What to Test First and Why

### 2.1 Auth — Magic-Link + Headless (signin/signup) (CRITICAL)

**Why it matters**: Every flow in Bunkai is gated by authentication. Four separate auth code paths exist — each has different session creation, error modes, and token issuance. A bug in any one path leaves a class of users locked out or unsecured.

**The four paths:**
- Magic-link: `POST /api/v1/auth/magic-link` → custom `magic_link_tokens` table (NOT Supabase native OTP)
- OAuth: GitHub / Google callback via `/auth/callback` (trigger UI absent from login page — callback route exists)
- Headless signin: `POST /api/v1/auth/signin` — email+password, auto-mints PAT in same response
- Headless signup: `POST /api/v1/auth/signup` — provisions user with `email_confirm: true` (skips email click), auto-mints PAT

**What commonly breaks:**
- Magic-link: `consumed_at` single-use enforced app-layer only — a race condition (two concurrent requests with the same token) could allow double-consumption
- Magic-link expiry: `expires_at` checked app-layer, not DB constraint — a misconfigured comparison (UTC vs local) burns valid tokens
- Headless signup: `email_confirm: true` bypasses email verification — verify this flag is not accidentally removed in staging config
- First-login workspace bootstrap: `bunkai_bootstrap_workspace` RPC is still used here (unlike ATC create — see §2.5) — verify RPC atomicity still holds
- OAuth callback: open-redirect guard on `next` param must reject non-root-relative URLs

**Dependencies**: Supabase Auth, `magic_link_tokens`, `magic_link_token_secrets`, `workspace_members`, JWT HttpOnly cookie, `middleware.ts`

**What an experienced QA would check:**
- Happy path: each of the 4 paths → session created → workspace accessible
- Magic-link replay: consume token once → try same URL again → `401` or `410`, not re-authenticated
- Headless signup with existing email → `409` (not `500` or silent)
- OAuth callback with tampered `next` param (absolute URL) → reject, not redirect
- Session persistence: page refresh after any auth path → still authenticated

### 2.2 Bearer PAT — Issuance + Scope Enforcement (CRITICAL)

**Why it matters**: This is the exclusive auth mechanism for AI agents and CI. **BK-134/135 is an open security bug**: member-role users can self-issue `workspace:admin` PATs. 136 such tokens are active on staging. A `member` with a `workspace:admin` PAT can call admin-gated endpoints they have no role-level right to reach.

**What commonly breaks:**
- **BK-134/135 (OPEN)**: `POST /api/v1/tokens` does not verify caller holds `admin` or `owner` role before minting `workspace:admin` scope — must return `403`, currently returns `201`
- Scope enforcement: `atc:read`-scoped token calling `POST /api/v1/atcs` → must `403`
- Plain token returned ONCE — a retry must NOT return the same plain secret
- SHA-256 hash stored in `access_token_secrets` (sibling table) — verify plain token never logged or appears in response body beyond initial issuance
- PATs cannot create PATs (chicken-and-egg) — a Bearer-authenticated request to `POST /api/v1/tokens` must return `403` with code `forbidden`
- `workspace_id`-bound token used against a different workspace's resources → `403`

**Scopes (confirmed):** `atc:read`, `atc:write`, `run:execute`, `workspace:admin`

**Dependencies**: `access_tokens`, `access_token_secrets` (secrets sibling), `middleware.ts`, every write endpoint

**What an experienced QA would check:**
- Member user mints `workspace:admin` PAT → must `403` (BK-134/135 fix verification)
- `atc:read` token → `GET /api/v1/tokens` → `200`; `POST /api/v1/atcs` → `403`
- Bearer token → `POST /api/v1/tokens` → `403` (PAT-from-PAT blocked)
- Revocation: `DELETE /api/v1/tokens/{id}` → next Bearer request → `401` (immediate, not cached)
- Expired token (`expires_at` in past) → `401` with clear error code

### 2.3 RLS Multi-Tenancy — Workspace Isolation (CRITICAL)

**Why it matters**: Postgres RLS is the last line of defense between tenants. If user from workspace A reads workspace B's ATCs, the breach is silent — no error thrown, just data returned. This is the hardest bug class to detect because it requires a multi-tenant test setup.

**What commonly breaks:**
- Missing `workspace_id` index on a table → RLS policy runs but does a seq scan under load, masking isolation breakage
- Service-role bypass (`SET LOCAL row_security = off`) leaking into user-context code paths
- RLS policy written for INSERT but missing for SELECT (common after migrations)
- `modules.path` materialized column: path rebuilt without workspace scoping → subtree query crosses tenant boundary

**Dependencies**: Every entity with `workspace_id`, Supabase Auth, `workspace_members` (RLS anchor)

**What an experienced QA would check:**
- Two users in different workspaces: user A queries any endpoint → zero rows from workspace B
- Direct Supabase query using workspace A's JWT → workspace B rows return empty (not 0, not error — empty)
- After schema migration adding a new entity, verify RLS policy exists before merging
- Archive cascade: archiving Module in workspace A must not touch entities in workspace B

### 2.4 ATC Create — App-Layer Atomicity (CRITICAL)

**Why it matters**: `bunkai_save_atc` SECURITY DEFINER RPC was removed. ATC creation now runs as an app-layer transaction in the Next.js route handler for `POST /api/v1/atcs`. The DB-layer atomicity guarantee is gone — a crash or network interrupt mid-request can leave orphan `atc_steps` or `atc_acceptance_criteria` rows without a parent `atcs` row. The structural traceability constraint (every ATC must link to ≥1 US + ≥1 AC) is also enforced in the app layer, not a DB constraint.

**The 4-table insert sequence (app-layer):**
1. INSERT `atcs` (layer required, `status='unrun'`, `version=1`)
2. INSERT `atc_steps[]` (ordered by position)
3. INSERT `atc_assertions[]` (ordered by position)
4. INSERT `atc_acceptance_criteria[]` (≥1 required, each AC must belong to the US)

**What commonly breaks:**
- Orphan `atc_steps`: infra crash after step 1 succeeds but before step 2 completes → orphan parent row exists with no steps
- AC validation bypass: `ac_ids` sent with IDs from a different `user_story_id` than the one in the body → must `400` with code `ac_outside_user_story`
- Module scope validation: `module_id` must be the US's module or a descendant within the same project → cross-project ATC must `422`
- `atc_steps` position ordering: two steps at the same position → deterministic sort breaks
- Realtime broadcast: after successful create, all subscribed tabs must refresh tree without manual reload

**Dependencies**: `atcs`, `atc_steps`, `atc_assertions`, `atc_acceptance_criteria`, `activity_log`, Supabase Realtime

**What an experienced QA would check:**
- Happy path (BK-18): `POST /api/v1/atcs` with 3 steps + 2 assertions + 2 AC links → verify all 4 tables have rows, `activity_log` has one entry, Realtime broadcasts to open tabs
- Orphan guard: POST with empty `ac_ids[]` → `400` (code: `missing_acceptance_criteria` or similar)
- AC cross-story: `ac_ids` pointing to a different US → `400` (code: `ac_outside_user_story`)
- **NEW (NEW-G5)**: Simulate partial failure — verify no orphan `atc_steps` rows without parent `atcs` after a mid-request crash
- Idempotency: same `Idempotency-Key` header twice → second response returns first result, no duplicate rows

### 2.5 Module Tree — CRUD + Cascade Archive (HIGH)

**Why it matters**: Soft-deleting a Module cascades to all descendants — child modules, user stories, acceptance criteria, ATCs — atomically via `DELETE /api/v1/modules/{id}`. The API returns counts of what was archived. A missing cascade leg means orphaned entities that pass RLS but are invisible in the UI. The materialized `path` column must stay consistent after every rename or move.

**Live as of 2026-06-13:**
- `modules.archived_at` confirmed in DB
- Cascade to `user_stories`, `acceptance_criteria`, `atcs` confirmed
- `path` rebuild on rename confirmed
- Cycle detection on move confirmed (422)
- Depth limit: soft warn at depth 5, hard block at depth > 6 (422)

**What commonly breaks:**
- Cascade missing a table: `atc_acceptance_criteria` rows not archived when ATC is cascade-archived
- Module move cycle: moving Module A under its own descendant → must `422`
- `path` stale after move: breadcrumbs and subtree filters return wrong results
- Re-archive: `DELETE` on already-archived module → `409` (confirmed behavior to verify)
- Archive response count: `{modules_count, stories_count, criteria_count, atcs_count}` must match actual DB state

**What an experienced QA would check:**
- Soft-delete parent module with 2 children + 3 grandchildren → verify all 5 descendant modules + their US/AC/ATC archived; response counts match
- Move Module A under Module B (valid) → verify `path` updated for A and all its descendants
- Attempt cycle: move Module A under its own child → `422`
- Rename module → breadcrumb in sibling module's path updates correctly
- Create 6 levels deep → `200`; create 7th level → `422`

### 2.6 Test Builder — ATC Chain Assembly (HIGH)

**Why it matters**: Test Builder (BK-27) is the foundation for the entire run execution layer. BK-28 (reorder), BK-32 (test view), BK-33 (test tags), and BK-34 (manual run start) are all blocked on it. The `tests` and `test_steps` tables exist in DB (schema only) — the API is landing soon. This is the next CRITICAL gate after ATC authoring.

**Structural constraints (from BK-27 story):**
- Test binds to active workspace at creation (immutable — no `project_id` or `module_id`)
- Title required (max 200 chars; whitespace-only rejected)
- Minimum 1 ATC in chain; duplicates allowed (ordered sequence, not set)
- Cross-workspace ATC refs rejected (RLS + app-level)
- Idempotency via `Idempotency-Key` header (24h TTL, scoped to `user_id + endpoint + key`)

**What commonly breaks:**
- Cross-workspace ATC reference: ATC from workspace B used in a Test from workspace A → must `403` or `422`, never silently accepted
- Workspace binding immutable: if a user switches active workspace mid-session, subsequent Test creates must still bind to the correct workspace
- Idempotency key collision: two Test creates with same key within 24h → second must return first Test, not create duplicate
- Whitespace-only title: `"   "` (3 spaces) must fail validation, not create a Test with an invisible title

**Dependencies**: `tests`, `test_steps`, `atcs`, `idempotency_keys`, `activity_log`

**What an experienced QA would check:**
- Happy path: create Test with 3 ATCs in order → verify `test_steps` rows with correct positions
- Cross-workspace ATC → rejected
- Duplicate ATCs in chain → accepted (sequence semantics, not set)
- Empty ATC list → rejected
- Idempotency replay within 24h → same Test returned, no duplicate

### 2.7 ATC Edit Propagation (HIGH)

**Why it matters**: Editing an ATC (via `PATCH /api/v1/atcs/{id}`) mutates the steps every chained Test executes. PATCH uses PUT-style semantics — omitted children are cleared. The `affected_test_ids` field currently returns `[]` (empty) in MVP because `test_steps` API is pending — but once Test Builder lands, this must propagate correctly.

**What commonly breaks:**
- Version bump not triggered: empty body → `200` no-op, no version bump. Non-empty body → `version++` and `atc.updated` event — verify both cases
- Clear semantics: omitting `steps` from PATCH body should clear all steps — not leave old steps in place
- `affected_test_ids` empty in MVP: once Test Builder is live, verify this field populates correctly
- Optimistic locking: `If-Match: <version>` header — stale version → `412`; absent header → no check (lenient mode)
- Concurrent edits: two agents PATCH same ATC simultaneously → last-write-wins; caller with `If-Match` wins the lock

**What an experienced QA would check:**
- Edit ATC title only → `version` incremented, steps unchanged
- PATCH with empty body → `200`, `version` NOT incremented
- PATCH omitting `steps` → steps cleared (PUT semantics)
- PATCH with stale `If-Match` version → `412` with `current_version` in body
- After BK-27 lands: edit ATC used by 2 Tests → `affected_test_ids` includes both Test IDs

### 2.8 Workspace Invite Lifecycle (HIGH)

**Why it matters**: Invites are the only onboarding path for new team members. Token is returned in the API response once — not emailed (MVP). If token expires or is revoked, the link is dead and there's no automatic re-notification. State machine has 5 transitions; the `rotated` path resets `accepted_at` and `revoked_at`, which is a subtle correctness risk.

**State transitions:** `pending → accepted | expired | revoked | rotated`

**What commonly breaks:**
- Email mismatch: caller's email must match `invite.email` exactly — case sensitivity matters
- Rotate path: `POST .../invites/{id}` resets `accepted_at` + `revoked_at` + generates new secret + extends expiry 7 days — verify all four fields change atomically
- Accept expired invite → `409` (not `401`)
- Accept revoked invite → `409`
- Already-accepted user re-invited: accept flow must upsert membership row, not fail

**What an experienced QA would check:**
- Happy path: issue invite → share token → accept as correct-email user → member row created
- Email mismatch: accept with wrong email → `403`
- Token expiry: accept after 7 days → `409` (need time-manipulation or direct DB expiry)
- Rotate: rotate invite → old token rejected → new token accepted
- Revoke: revoke invite → token rejected even within 7-day window
- Resend to already-accepted user → upserts membership, no error

## 3. State Machines That Matter

### 3.1 `modules` — Operational (Live)

Archive is terminal; no unarchive path exists. Cascade is atomic: one DELETE archives the entire subtree.

- **Most likely broken**: cascade not including `atc_acceptance_criteria` join table rows when ATCs are archived
- **Terminal guard**: re-archive attempt must return `409`
- **Silent corruption**: archived module's entities that pass RLS but don't appear in UI — only detectable via DB query

### 3.2 `user_stories.status` — Partially Documented (NEW-G3)

`status` column is live with default `'draft'`. AC delete endpoint fires `user_story_reverted` event when last active AC is deleted. Additional valid states (`ready_to_test`, etc.) are inferred but not confirmed in schema.

- **Why it matters**: if valid transitions are wrong, US lifecycle tests will fail on valid state changes or pass on invalid ones
- **Action required**: enumerate valid `status` values before writing US lifecycle tests — see NEW-G3 in §11

### 3.3 `workspace_invites` — Security

7-day expiry enforced app-layer (not DB constraint). Rotated state resets all prior lifecycle fields.

- **Most likely broken**: `rotated` path doesn't clear `accepted_at` — old acceptance appears valid to the API check
- **Invisible**: a revoked invite's token rejection is only verifiable by attempting to use it

### 3.4 `access_tokens` — Security

Implicit status derived from `expires_at IS NULL OR expires_at > now()` AND `revoked_at IS NULL`. No single column — computed in `middleware.ts` on every request.

- **Critical**: revocation must reflect on the very next request (no caching)
- **Known gap (NEW-G1)**: hash storage location is in `access_token_secrets` sibling table — not visible via DBHub; confirm before writing PAT security tests

### 3.5 `import_jobs` — Operational (Live)

```
queued → running → completed
                └→ failed
```

Constraint: at most one active (`queued` or `running`) import per project → `409` on concurrent attempt. `next_page_token` tracks Jira pagination cursor — enables resumable large imports.

- **Silent failure**: `status=failed` with per-issue `errors[]` — partial success is valid; detect by polling `/api/v1/imports/{id}`

### 3.6 `atcs.status` — Execution-Gated (Partially Live)

Default `'unrun'`. Transitions to `passed`/`failed` will be set by Phase 2 run execution. Only `'unrun'` is a confirmed value today.

### 3.7 `magic_link_tokens` — Security (Live)

```
issued → pending (consumed_at IS NULL, now() < expires_at)
      → consumed (consumed_at SET — single-use, app-layer)
      → expired (now() > expires_at — app-layer check)
```

- **Most likely broken**: two concurrent requests with the same token — app-layer single-use check is not atomic; potential race between check and SET

## 4. Silent Killers — Automated Processes

### 4.1 `bunkai_atcs_refresh_tsv` (DB trigger on ATCs INSERT/UPDATE)

**What it does**: Recomputes `tsv` tsvector from title + tags. Enables full-text ATC search (GIN index) without external search service.

**What breaks if it fails**: ATC search and autocomplete returns stale or missing results. A newly created ATC with a distinctive title won't appear in search. Users assume no ATC exists and create a duplicate — defeating the reuse model.

**How failure is detected today**: Not detectable without searching for a known-just-created ATC.

**Recommended QA strategy**: Create ATC with a unique title token → immediately search for that token → verify it appears in results with correct `ts_rank`. Repeat after an ATC edit (title change).

### 4.2 `bunkai_set_updated_at` (DB trigger on multiple tables)

**What it does**: Sets `updated_at = now()` on UPDATE across all tracked tables.

**What breaks if it fails**: `updated_at` is stale → optimistic locking comparisons and audit timestamps incorrect. Silent — no user-visible error.

**Recommended QA strategy**: UPDATE any tracked entity → verify `updated_at` changed to within 1 second of the request timestamp.

### 4.3 Jira Import Worker (async, Vercel Cron)

**What it does**: Background worker processes `import_jobs` in `queued` state — paginates Jira issues via JQL, upserts `user_stories` by `external_id`, tracks `created_count / updated_count / skipped_count / errors`.

**What breaks if it fails**: User Stories don't appear in Bunkai. Import row may be stuck `queued` or `running` forever. Since dedup is by `external_id`, a missed import is recoverable by re-triggering — but only if the user knows to retry.

**How failure is detected today**: `GET /api/v1/imports/{id}` polling endpoint returns `status`. No push notification in MVP. User must actively poll.

**Recommended QA strategy**:
- Queue Jira import → poll until `completed` → verify `user_stories` rows with correct `external_id`
- Re-trigger same JQL import → verify no duplicate `user_stories` (dedup by `external_id`)
- Concurrent import attempt on same project → must `409`
- Simulate per-issue error (bad JQL for one issue) → import `status=completed` with `errors[]` populated (partial success)

### 4.4 `idempotency-cleanup` Cron (Hourly — Vercel)

**What it does**: Deletes `idempotency_keys` rows older than 24h. Keeps table bounded.

**What breaks if it fails**: Table grows unbounded. After 24h + missed cleanup, `Idempotency-Key` from 25h ago should create a new resource — but a stale row may return the old cached response instead. Also, storage pressure.

**How failure is detected today**: Table size only — no alert defined.

**Recommended QA strategy**: Verify that an `Idempotency-Key` used >24h ago allows creation of a new resource (not replayed). Requires time-based test or direct DB manipulation.

### 4.5 Supabase Realtime Subscriptions (ATCs, Import Jobs)

**What it does**: ATC create/update events → subscribed browser tabs refresh tree node. Import job progress → UI progress updates (polling fallback also available).

**What breaks if it fails**: Tree view doesn't update after ATC create without page reload. Import progress bar frozen until manual refresh.

**How failure is detected today**: Only by observing the UI — no backend alert. Supabase Realtime is infrastructure-managed; connection drops silently.

**Recommended QA strategy**: Create ATC in tab A → verify tab B tree updates without reload. Start Jira import → verify progress updates appear in UI (confirm Realtime vs polling path).

## 5. External Integrations — Failure Points

### 5.1 Supabase Auth

- **Which flow stops if down**: ALL UI flows. No login = no access.
- **Bearer PAT exception**: if middleware validates token hash from Postgres directly (bypassing Auth service), headless flows may survive a Supabase Auth outage.
- **Critical timeout**: JWT is 1h access + 30d refresh. If the refresh endpoint is unreachable, users get logged out after 1h.
- **Acceptable degradation**: None for UI users — Auth is a hard dependency.
- **Known quirk**: OAuth callback open-redirect guard must reject non-root-relative `next` params server-side.

### 5.2 Jira (Atlassian)

- **Which flow stops if down**: Jira import (`POST /api/v1/imports`). Core flows — ATC authoring, workspace management — are unaffected.
- **Acceptable degradation**: Import → `import_jobs.status=failed` with per-issue `errors[]`. User can retry. Retrigger is safe (idempotent by `external_id`).
- **Known quirk (NEW-G4)**: Jira auth config mechanism unconfirmed. `integrations` config table is NOT in DB. Credentials likely wired via env vars (`JIRA_HOST`, `JIRA_TOKEN`) — verify before writing import tests.
- **Known quirk**: Jira REST rate limits. Import pagination firing many requests per minute may get `429`. Worker must handle with backoff and resume from `next_page_token`.

### 5.3 Cloudflare R2 / MinIO

- **Status**: Phase 2 — evidence uploads for Run steps and bugs. Not testable yet.
- **Acceptable degradation (when live)**: Step records result with null `evidence_url`. Run can still complete. Known quirk: signed URL TTL expiry on large video trace uploads.

### 5.4 Vercel Cron

- **Which flows stop if down**: `idempotency-cleanup` (table grows), `run-timeout-sweeper` (Phase 2), `jira-bug-sync-retry` (Phase 2).
- **Acceptable degradation**: System continues for active users. Degradation is invisible and cumulative.

### 5.5 Supabase Realtime

- **Which flows degrade**: ATC tree refresh, import progress updates. Both have polling fallbacks.
- **Acceptable degradation**: Polling fallback for import; manual page reload for ATC tree. Neither is a hard failure.

## 6. Dependency Cascade Between Flows

```
Supabase Auth
  └─► JWT / PAT validated by middleware.ts
        └─► RLS workspace isolation
              ├─► Workspace + Invite flows
              │     └─► Project → Module (cascade archive live)
              │           └─► User Story → Acceptance Criteria
              │                 └─► ATC create (app-layer 4-table transaction)
              │                       └─► Tests (chain ATCs) [BK-27 landing]
              │                             └─► Run execution [Phase 2]
              │                                   └─► Bug filing [Phase 2]
              │
              └─► Bearer PAT ───────────────────┐
                    └─► Scope enforcement       │
                          └─► All write ops ◄──┘
                                └─► Idempotency keys (24h TTL)
                                      └─► Safe retry for ATC create + Test create
```

**Most critical chain**: Auth → RLS → ATC create → Test assembly → Run execution. Each link's failure blocks everything downstream.

**Current production risk chain**: `POST /api/v1/tokens` (no role gate) → member user mints `workspace:admin` PAT → PAT bypasses role enforcement on admin-gated endpoints → privilege escalation. This chain is LIVE.

**Second critical chain**: ATC create (app-layer) → infra crash → orphan `atc_steps` → GIN index triggered on orphan → search returns ghost ATC fragments. No DB-level constraint catches this.

## 7. Edge Cases Developers Commonly Forget

### Concurrency
- Two users create an ATC with the same slug simultaneously in the same module → unique constraint violation must surface as `409`, not `500`
- Two agents start the same Test with the same `Idempotency-Key` within 24h → second call must return the first `run_id`, not create a duplicate *(Phase 2)*
- `magic_link_tokens.consumed_at` race: two concurrent requests with the same token → only one should succeed; app-layer check is not atomic

### Data Limits
- `modules` tree depth: creating level 7 (cap is 6) → must be blocked server-side (`422`), not just in UI
- `atc_steps` position ordering: 100+ steps in one ATC → rebalance must produce unique positions; PATCH replace-all at this scale must not exceed request body limits
- Workspace slug: 3–40 chars, reserved slug protection (20+ reserved words) — test boundary values and reserved list exhaustively

### Orphaned States (Live Risk)
- ATC with `user_story_id` pointing to an archived US — cascade archives the ATC, but verify: does ATC appear in search results after cascade? GIN index on archived ATC should not surface in FTS results.
- `accepted_at` on an invite that was subsequently rotated — `rotate` clears `accepted_at`; verify the old acceptance is truly invalidated (token hash changed)

### Idempotency
- POST `/api/v1/imports` with the same `project_id` while a prior import is `queued` or `running` → `409`
- `Idempotency-Key` reuse after 24h TTL expires → new resource created (not replayed stale result)
- ATC create with `Idempotency-Key` + same key on edit (`PATCH`) → keys are endpoint-scoped; should not collide

### Permission Boundaries
- `viewer` user calling `POST /api/v1/atcs` → `403` (authenticated, unauthorized — not `401`)
- `member` user calling `PATCH /api/v1/workspaces/{id}` → `403` (owner-only)
- PAT with `workspace_id` binding calling an endpoint in a different workspace → `403`
- **BK-134/135**: `member` user calling `POST /api/v1/tokens` with `workspace:admin` scope → must `403` after fix lands

### Timezone / DST
- `workspace_invites.expires_at`: 7 days from creation in UTC — if server generates in local time and verification is UTC, invites expire at unexpected times
- `import_jobs.started_at` / `completed_at`: both must be UTC ISO-8601; durations should use UTC diff, not wall clock
